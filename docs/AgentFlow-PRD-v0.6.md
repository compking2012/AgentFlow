# AgentFlow 产品需求文档

版本：v0.6 · 2026-09-21

## 1. 产品目标

AgentFlow 让单个用户围绕一个长期产品目标，创建或导入产品、持续增加需求，由专业 Agent 完成分析、PRD、架构、开发、审查、测试和本地交付。用户通过工作台了解谁在执行、当前阶段应产出什么、产物在哪里以及质量是否满足交付条件。

产品目标与一轮新增需求分别保存。新增需求描述本次增量，不覆盖原始目标；每轮形成独立运行、预算、产物版本和交付记录。人工审核可以应用于任意阶段，驳回会使相关后续版本重新验证。

## 2. 调整统一对照

| 主题 | 已有交互 | 当前要求 |
| --- | --- | --- |
| 平台 | 创建入口选择 Web 或 API | 产品声明多平台；展示七类平台及其可执行状态 |
| 项目入口 | 创建产品和项目与目标分离 | 创建与导入在同一产品入口，移除项目与目标导航 |
| 持续迭代 | 主要围绕单次运行 | 新增需求归属已有产品，从 PRD 开始建立新迭代 |
| 执行台 | 平铺全部任务及依赖表 | 外层阶段、内层并行任务和明确的汇总节点 |
| 产物 | JSON 与证据对象为主 | 默认展示具名文档、完整源码和测试代码目录 |
| 质量 | 平台检查状态为主 | 增加实际用例通过率、审查问题、测量指标和证据入口 |

## 3. 入口与页面

主导航包含：**创建产品、新增需求、执行台、人工审核、产物与质量、本地设置**。

创建产品页提供“从头创建”“导入已有项目”两种方式，并展示产品列表。选中产品后可以查看历次迭代、进入当前执行、下载交付和启动已交付版本。工作台用产品名称和迭代需求区分运行，不能仅靠 UUID 辨认。

公开 CLI 继续保持 `start`、`run`、`status`、`launch`、`stop` 五个命令。长期运行参数、模型和默认策略来自 `~/.config/agentflow/config.toml`；本次交互扩展以 WebUI 为入口。

## 4. 产品创建与多平台

### 4.1 平台模型

产品平台是集合，不是互斥单选。可声明 Web、API、iOS、Android、Windows、macOS、Linux。声明的平台与实际已验证的平台分开记录。

| 平台 | 本机产品入口状态 |
| --- | --- |
| Web、API | 支持当前受管 Node.js Web/API 工具链，可组合使用 |
| iOS、Android、Windows、macOS、Linux 原生应用 | 展示“暂不支持”；可作为导入诊断和产品元数据保留，禁止承诺已支持自动执行 |

新建选择未支持目标时，界面和服务端都必须明确阻止自动启动。不能悄悄移除原生平台后把 Web 成功显示为整个多平台产品成功。

### 4.2 从头创建

输入产品名称、产品目标、平台集合，选择人审策略，输出目录可选。平台准备本机执行环境，启动目标整理至交付的全流程。输出目录必须为新目录或空目录。

### 4.3 导入已有项目

用户提供本机项目目录。系统先进行只读诊断，依据实际文件、项目清单、入口和工具配置识别平台及技术特征，并展示判断依据、未识别项和支持限制。识别到多个平台时保留整个集合；无法确定时明确提示，不能猜测为 Web。

用户确认或补充产品名称、长期产品目标后登记产品。导入需保留原代码和 Git 基线，不覆盖原工作区，不执行项目中的安装或构建脚本来完成“诊断”。现阶段执行需要有明确提交基线的 Git 项目；未提交变更、未知工具链和未支持平台都必须给出具体处理信息。

产品可登记后再增加需求。静态诊断报告只能说明读到的代码特征，不得标成已经完成市场调研、代码审查或测试。

## 5. 新增需求与增量迭代

“新增需求”页选择产品，展示不可在本次表单修改的产品目标，填写需求名称、需求描述和验收期望，并列出已有代码与文档基线。

默认流程：

```mermaid
flowchart LR
  A[已有产品与确认基线] --> B[新增需求记录]
  B --> C[更新 PRD]
  C --> D[需求拆解]
  D --> E[架构影响检查与必要调整]
  E --> F[开发任务规划]
  F --> G[开发及独立审查]
  G --> H[单元和集成测试]
  H --> I[新版本交付]
```

本轮复用同一产品的有效目标说明、调研资料和架构资料，通常不重新执行目标整理或调研。没有这些历史产物的导入项目，以明确标识的用户输入与静态诊断作为背景，不制造“Agent 已调研”的历史。

每轮都保留架构阶段。它先判断变更对模块、接口、数据、安全、性能与扩展性的影响；适用时沿用原架构并解释原因，必要时更新图、接口和迁移方案。新增或删除 API、数据兼容性变化、跨模块依赖等不能被忽略。

增量开发基于已确认交付的准确提交；导入后的首轮基于确认的导入提交。已有交付包保留，新包按运行版本保存。正在执行的迭代或尚未停止的产品预览需要先明确处理，防止并发修改同一产品或误把旧预览当作新版本。

新增需求不是重试按钮。重试沿用原运行的责任和历史；新需求创建新的迭代预算，并记录基线运行关系。大幅改变产品定位的请求应明确作为范围调整处理。

## 6. 执行台与阶段产物

每个阶段节点同时显示：阶段名称、状态、负责角色及活跃 Agent 数、目标产物、实际产物名称、工作目录位置和阻塞原因。移除独立“工作项与依赖”表，依赖由节点连接表达，技术追溯信息可以按需展开。

| 阶段 | 目标产物 |
| --- | --- |
| 目标整理 | 产品目标说明：对原始目标重构，明确用户、范围、假设和成功标准 |
| 调研分析 | 产品与技术调研报告：来源、竞品/方案、结论及未验证信息 |
| 产品需求 | PRD：需求范围、用户流程、稳定需求编号及验收条件 |
| 需求拆解 | 需求清单与依赖、正常/异常验收场景 |
| 系统架构 | 架构说明、Mermaid 图、主要 API、数据模型、变更影响与决策 |
| 开发任务规划 | 可执行任务、分工、依赖、文件范围和验证要求 |
| 功能实现 | 完整项目源码快照与变更说明 |
| 代码审查 | 准确版本的审查报告、问题位置、分类、严重程度及建议 |
| 单元测试设计/编写 | 单测方案、需求映射和实际测试代码 |
| 集成测试设计/编写 | 平台工具方案、集成场景、测量方案和实际测试代码 |
| 单元/集成测试执行 | 用例结果、通过率、失败详情、耗时和有来源的测量值 |
| 代码交付 | 完整代码、运行包、研发文档、测试报告及本地 Git 交付说明 |

阶段拆成 N 个任务时，外层仍显示一个阶段。展开后显示 N 个具名任务以及最后的“阶段名称汇总”，例如“调研分析汇总”“功能实现汇总”“集成测试编写汇总”。外层只显示该阶段的统一产物；子任务产物在内部查看。

汇总不是装饰节点：文档需要形成统一结论，代码需要真实合并和冲突检查，测试代码需要完整的可执行集合。子任务失败、合并冲突或汇总未完成时，外层不能显示已完成。

## 7. 人类可读产物

默认产物形态只有三类：

1. 可阅读的 Markdown 文档和报告，可预览和下载。
2. 当前版本完整项目代码目录，显示准确提交及所在工作目录。
3. 项目中的单元/集成测试代码目录及其说明。

文档名称应描述内容。平台在阶段产物采集后保存相应文档到工作目录，并绑定运行、工作项、版本和原始内容摘要。文档修改或路径被替换时，保留原文件并明确报错，不静默覆盖用户改动。

JSON、原始测试报告和清单仍用于内部结构化处理与证据校验，默认产物列表不以这些对象替代报告。文档预览不执行 HTML 或脚本。PDF 可作为后续导出格式，MVP 的 Markdown 应完整可读。

## 8. 产物与质量

单元测试和集成测试分别显示：已发现用例数、通过、失败、错误、跳过、未确认、通过率、测试执行耗时和报告入口。通过率以当前候选、当前平台矩阵的有效原始用例为依据，跳过不算通过；没有执行证据、矩阵不完整或报告损坏时不得显示 100%。

代码问题显示类别、严重程度、文件、描述、来源和状态。Agent 静态审查与实际运行的检查器分别标识。未分类问题不能全部当作 bug，失败用例数量也不能直接换算成 bug 数量。独立格式检查未执行时明确说明。

性能面板展示有测试来源、单位和样本数的实际测量，例如 API P95 响应时间。测试套件耗时不是应用响应时间；没有测量时显示“未测”，不填零值或估计值。

只有代码审查、要求的单元/集成测试、平台矩阵和所选人审门禁均满足后才交付。派生 Markdown 或用户点击审核不能把失败、未知或旧版本证据改成通过。

## 9. MVP 验收

- 七个平台在创建页可辨认，多平台可表达；Web/API 可启动，未支持原生目标无法绕过服务端启动限制。
- 已有 Git 项目导入保留代码；诊断有具体依据，未知类型不伪报；名称和目标可补齐。
- 主导航不再包含“项目与目标”，导入与创建都从产品入口进入。
- 新需求保持原目标，建立新运行，从 PRD 开始；同项目旧文档可复用，跨项目/陈旧输入拒绝。
- 新版本使用确认基线，架构阶段仍执行，旧交付包和历史运行保持可追溯。
- 工作流能展开并行任务和汇总，外层每阶段一个统一产物，没有重复依赖表。
- 文档实际落盘并可预览，源码/测试目录指向真实版本，默认不展示机器 JSON。
- 用例通过率、问题列表和性能来源有正反例测试；无证据/旧候选/跳过/损坏报告不得假通过。
- 重试、并发、恢复、审批和交付仍遵守同一写入者、版本、fence 和幂等约束。

实现与约束见 [MVP 架构与实现方案 v0.4](AgentFlow-MVP-产品工作台架构与实现方案-v0.4.md)。
