# AgentFlow 产品需求文档

版本：v0.8 · 更新于 2026-09-29

## 1. 产品目标

AgentFlow 让单个用户围绕一个长期产品目标，创建或导入产品、持续增加需求，由专业 Agent 完成分析、PRD、架构、开发、审查、测试和本地交付。用户通过工作台了解谁在执行、当前阶段应产出什么、产物在哪里以及质量是否满足交付条件。

产品目标与一轮需求变更分别保存。需求变更描述本次增量，不覆盖原始目标；每轮形成独立运行、预算、产物版本和交付记录。产品负责人也可以显式修改目标或平台，此时保存新的产品配置版本，必须另行确认从头运行；旧目标、运行和交付作为历史保留。人工审核可以应用于任意阶段，驳回会使相关后续版本重新验证。

## 2. 调整统一对照

| 主题 | 已有交互 | 当前要求 |
| --- | --- | --- |
| 平台 | 创建入口选择 Web 或 API | 产品声明多平台；展示七类平台及其可执行状态 |
| 项目入口 | 创建产品与已有产品管理混在一起 | 创建/导入集中在“创建产品”；独立“我的产品”管理既有产品，受理后进入对应产品 |
| 产品管理 | 主要提供查看和交付操作 | 支持改名、编辑未来默认、软删除和恢复；磁盘文件、运行及交付历史保留 |
| 关键配置 | 修改目标与继续旧运行边界不明确 | goal/targets 改变后标记 needs_restart；显式从头运行才创建完整新 Run 和新 Iteration |
| 原运行恢复 | 依赖通用暂停或返工入口 | 明确 retry/continue，保留成功上游与兄弟，只重做失败和受影响部分，预算不自动增加 |
| 会话交互 | 锁定按钮及重新连接操作打断使用 | 移除锁定功能；同一标签页刷新及所有者凭据到期时自动续接，首次与控制器重启仍需本机启动链接 |
| 持续迭代 | 主要围绕单次运行 | 需求变更归属已有产品，从 PRD 开始建立新迭代 |
| 执行台 | 平铺全部任务及依赖表，返工会增加阶段节点 | 每个逻辑阶段一个节点；并行任务、返工和重试在节点内查看 |
| 产物 | JSON 与证据对象为主，每次返工产生独立 Markdown | 默认展示具名文档、完整源码和测试代码目录；每阶段一份当前文档，文内汇总历史问题与处理 |
| 恢复说明 | 逐条展示历史模型用量确认段落 | 已确认项隐藏，待处理项集中在默认收起的恢复入口 |
| 质量 | 平台检查状态为主 | 增加实际用例通过率、审查问题、测量指标和证据入口 |
| 文档语言 | 未显式设置 | 产品级默认中文，可选择英文，文档与新增修改注释遵循运行语言快照 |
| 文档专业性 | 上游材料与实现约束混合 | 各阶段按受众、内容边界和必要信息撰写，简单产品简写 |
| 工作流视图 | 展开式阶段列表 | 可折行的工作流全图，当前执行节点高亮，点击查看产物与任务详情 |
| 模型调用次数 | 默认 200 次，仅允许有限上限 | 默认仍为 200；整数 `0` 表示不限，正数 `1` 至 `2000` 表示有限上限 |
| 单次模型输出额度 | 旧运行沿用创建时额度，SDK 默认值可能进一步压低 | 同一模型的新执行读取固定配置文件中的最新额度，日志显示实际值与来源；已开始执行和历史保留原值 |
| 需求变更入口 | 只描述增加需求 | 使用“需求变更”，支持增加、调整和删除功能，保留产品目标 |
| 项目工作流 | 按运行选择，变更流程只显示执行的后半段 | 先选项目再选需求变更；显示同一完整阶段图，前置阶段注明沿用基线 |
| 文档连续性 | 每次运行在 GUID 目录生成文档 | `documents/<阶段>/<文档>.md` 维护当前完整内容，前部记录变更历史；历史查看独立快照 |

## 3. 入口与页面

主导航包含：**创建产品、我的产品、需求变更、执行台、人工审核、产物与质量、本地设置**。

“本地设置”提供统一的执行设置。用户能够查看并修改应用决定的调用次数、工具次数、时长、并行数量和自动恢复等限制，明确看到默认值、配置文件值、已生效值以及修改对既有工作的影响。模型输出长度和推理设置遵循对应模型配置，不设置重复的应用值。保存必须保留未修改字段；发生并发编辑或保存结果未知时，保留用户输入并提供核对方式，不覆盖其他修改或重复保存。

“创建产品”专注于从头创建和导入已有项目；提交成功后进入“我的产品”并选中对应产品。“我的产品”提供搜索、使用中/已删除列表、详情和管理操作，可查看历次运行、进入当前执行、下载交付和启动已交付版本。工作台用产品名称和迭代需求区分运行，不能仅靠 UUID 辨认。

首次打开需通过 `agentflow start` 提供的本机启动链接建立会话。已有标签页刷新或所有者凭据到期时自动续接。页面没有锁定按钮；无法续接时显示“打开本机工作台”连接页。控制器重启、续接票据七天未使用而过期或标签页无法保留票据时，需再次使用本机启动链接。连接恢复不会重新创建研发任务，也不会自动重试结果未知的业务提交。

浏览器的 owner 管理凭据仅保留在页面内存；受限续接票据仅保存在按 origin 和端口隔离的 `sessionStorage`，不使用 Cookie 或 localStorage。票据只能调用会话续接接口，不能直接管理产品或运行；成功使用后滚动续期七天。后台继续检查精确 Host/Origin，明确认证失败后的业务重发保留原幂等键。

公开 CLI 继续保持 `start`、`run`、`status`、`launch`、`stop` 五个命令。长期运行参数、模型和默认策略来自 `~/.config/agentflow/config.toml`；本次交互扩展以 WebUI 为入口。

## 4. 产品创建与多平台

### 4.1 平台模型

产品平台是集合，不是互斥单选。可声明 Web、API、iOS、Android、Windows、macOS、Linux。声明的平台与实际已验证的平台分开记录。

| 平台 | 本机产品入口状态 |
| --- | --- |
| Web、API | 支持当前受管 Node.js Web/API 工具链，可组合使用 |
| iOS、Android、Windows、macOS、Linux 原生应用 | 展示“暂不支持”；可作为导入诊断和产品元数据保留，禁止承诺已支持自动执行 |

新建选择未支持目标时，界面和服务端都必须明确阻止自动启动。不能悄悄移除原生平台后把 Web 成功显示为整个多平台产品成功。

### 4.2 从头创建

输入产品名称、产品目标、平台集合，选择人审策略，输出目录可选。平台准备本机执行环境，启动目标整理至交付的全流程。输出目录必须为新目录或空目录。

### 4.3 导入已有项目

用户提供本机项目目录。系统先进行只读诊断，依据实际文件、项目清单、入口和工具配置识别平台及技术特征，并展示判断依据、未识别项和支持限制。识别到多个平台时保留整个集合；无法确定时明确提示，不能猜测为 Web。

用户确认或补充产品名称、长期产品目标后登记产品。导入需保留原代码和 Git 基线，不覆盖原工作区，不执行项目中的安装或构建脚本来完成“诊断”。现阶段执行需要有明确提交基线的 Git 项目；未提交变更、未知工具链和未支持平台都必须给出具体处理信息。

登记后在“我的产品”选择从头运行完整流程，或在具备可用基线时增加需求。静态诊断报告只能说明读到的代码特征，不得标成已经完成市场调研、代码审查或测试。

### 4.4 文档和注释语言

产品的“文档与注释语言”默认简体中文，可选择 English。创建和导入时可设置，已有产品在无活跃执行且预览已停止时可修改未来默认；需求变更提交时可选择本轮语言。CLI 不新增语言参数，默认值在固定配置的 `[product] language = "zh-CN"` 中设置。

每轮接受任务时冻结语言，运行中的文档、报告及新增或修改的解释性代码注释使用该语言。修改产品默认不重写既有产物，也不改变已经接受的运行；机器字段、标识符、API 名称、路径及引文原题保持原样。新要求需要按新的运行或返工版本产生可追溯产物。

### 4.5 模型调用次数

固定 TOML 的 `[product] max_model_requests` 默认 `200`，CLI 不增加参数。新建、导入和需求迭代正确继承 `0`，不能把它当作缺省值回退为 200；已接受请求保留原次数快照和幂等标识。

| 输入 | 产品与界面行为 |
| --- | --- |
| 整数 `0` | 模型调用“不限次数”，不能显示为“0 次”或零费用 |
| 整数 `1` 至 `2000` | 使用指定次数上限 |
| 负数、布尔、非整数、数字字符串或超过 `2000` | 拒绝，不隐式转换 |
| 用户已编辑的 `0` | 定时刷新不能用默认有限值覆盖 |

不限次数仅解除调用次数约束；每次模型输出、工具调用、执行时长和费用控制仍按原规则生效。实际费用由供应商计费，没有可靠价格时保持未知。默认变更不自动修改或恢复已有运行；调整当前有限额度或改为不限必须由所有者明确操作，并保留用量、费用与审计记录。

### 4.6 我的产品：编辑、回收站与从头运行

| 操作 | 产品行为 | 对已有运行的影响 |
| --- | --- | --- |
| 改名 | 更新产品名称 | 不重跑，不重命名磁盘目录，不改已接受运行的快照 |
| 修改语言、默认调用次数或人审策略 | 保存未来运行的默认值 | 不改当前运行的语言、额度或已确认门禁，不强制重跑 |
| 修改产品目标或平台 | 保存新配置版本，显示“需从头运行” | 旧产物仅作为历史，不作为新目标已经完成的依据 |
| 从头运行 | 所有者单独确认后，按当前配置创建完整新运行及新迭代 | 从目标整理至交付重新执行，旧运行、额度和产物不清零、不覆盖 |
| 删除产品 | 移入“已删除产品”，默认列表隐藏 | 保留源码、导入原项目、运行记录、交付包和目录归属 |
| 恢复产品 | 从回收站恢复到“我的产品” | 不自动启动模型、恢复调度或重置状态 |

编辑和删除前必须确认产品预览、准备任务、活跃或未知 Agent、节点作业及未核对模型调用均已处理。暂停运行也必须等待已派发工作结束；不满足条件时显示具体阻塞原因，不能只把按钮禁用而不解释。

关键配置保存本身不调用模型。页面显示配置已更新并提供独立“从头运行”动作；此时不能把旧运行的成功状态、下载或启动入口当作新配置已交付。新运行从目标整理、调研、PRD、架构直至质量门禁和交付完整推进，不复用旧阶段的完成状态；源代码可从经核对的原项目或确认交付提交继续演进。导入产品保持原仓库，不用模板覆盖原文件。

所有管理写操作校验产品修订并使用幂等标识。关键配置版本、当前运行对应版本和历史运行关系均可追溯；旧提交重放不得额外创建产品或运行。已删除产品及配置过期的旧运行不能通过低层恢复操作绕过管理要求。

## 5. 需求变更与增量迭代

“需求变更”页选择产品，展示不可在本次表单修改的产品目标，填写需求名称、需求描述和验收期望，并列出已有代码与文档基线。

默认流程：

```mermaid
flowchart LR
  A[已有产品与确认基线] --> B[需求变更记录]
  B --> C[更新 PRD]
  C --> D[需求拆解]
  D --> E[架构影响检查与必要调整]
  E --> F[开发任务规划]
  F --> G[开发及独立审查]
  G --> H[单元和集成测试]
  H --> I[新版本交付]
```

本轮复用同一产品的有效目标说明、调研资料和架构资料，通常不重新执行目标整理或调研。没有这些历史产物的导入项目，以明确标识的用户输入与静态诊断作为背景，不制造“Agent 已调研”的历史。

每轮都保留架构阶段。它先判断变更对模块、接口、数据、安全、性能与扩展性的影响；适用时沿用原架构并解释原因，必要时更新图、接口和迁移方案。新增或删除 API、数据兼容性变化、跨模块依赖等不能被忽略。

增量开发基于已确认交付的准确提交；导入后的首轮基于确认的导入提交。已有交付包保留，新包按运行版本保存。正在执行的迭代或尚未停止的产品预览需要先明确处理，防止并发修改同一产品或误把旧预览当作新版本。

需求变更不是重试按钮。重试沿用原运行的责任和历史；新需求创建新的迭代预算，并记录基线运行关系。需要改变产品目标或平台时，在“我的产品”编辑关键配置并确认从头运行；不要把它包装成原运行的重试。

## 6. 执行台与阶段产物

每个逻辑阶段在主图中只出现一次。返工和重试更新该节点的当前状态，历史执行在节点内展开查看；已经处理的历史失败不影响当前完成状态，当前并行任务的失败和活动仍必须显示。连线表示正常研发阶段的前向依赖，不绘制返工回跳产生的循环。单元测试代码审查和集成测试代码审查分别保留独立阶段。

每个项目每阶段维护一份当前 Markdown，位于 `documents/<阶段>/<文档>.md`。每次变更基于已有文档更新完整内容，保留未受影响内容；文档前部记录变更名称、日期和调整摘要，并保留历史问题及处理结果。尚在返工时明确说明当前结果未完成。系统整理能够核验的旧生成副本，保留用户修改过的文件和底层审计证据。已确认的模型用量记录不逐条显示；尚需操作时使用一个默认收起的“处理恢复条件”入口。

工作台以项目为主选择项，另一个选择框切换初始研发与历次需求变更。图上始终保留完整研发阶段，切换后显示该次变更的状态与快照。从中间开始的变更将前置步骤标为已完成、注明沿用来源，不新增伪造的执行或质量记录。导入项目的目标与调研背景分别注明用户输入与静态诊断；尚在准备、没有运行记录的变更单独显示准备状态。历史文档查看不能覆盖当前磁盘文档或变更当前运行的操作目标。

执行台以可折行的工作流全图展示所有阶段及实际依赖。节点简洁显示阶段、状态和目标产物；正在执行的阶段持续高亮，选中状态与运行状态分开表达。失败、阻塞、待人审和完成状态有文字及视觉标识，不能只依赖颜色。

点击或通过键盘选择节点后，详情区展示负责角色、并行任务、汇总任务、实际产物、工作目录位置及具体阻塞原因。首次进入可以定位正在执行或需要处理的阶段；刷新不能覆盖用户主动选择。详情不挤占整个全图，不重新出现平铺的工作项与依赖表。

| 阶段 | 目标产物 |
| --- | --- |
| 目标整理 | 产品目标说明：润色和完善原始目标，明确用户、范围、假设和成功标准 |
| 调研分析 | 市场与竞品调研报告：竞品能力、竞争力、商业模式、真实用户反馈、来源与未验证信息 |
| 产品需求 | PRD：需求范围、用户流程、稳定需求编号及验收条件 |
| 需求拆解 | 需求清单与依赖、正常/异常验收场景 |
| 系统架构 | 架构说明、Mermaid 图、主要 API、数据模型、变更影响与决策 |
| 开发任务规划 | 可执行任务、分工、依赖、文件范围和验证要求 |
| 功能实现 | 完整项目源码快照与变更说明 |
| 代码审查 | 准确版本的审查报告、问题位置、分类、严重程度及建议 |
| 单元测试设计/编写 | 单测方案、需求映射和实际测试代码 |
| 集成测试设计/编写 | 平台工具方案、集成场景、测量方案和实际测试代码 |
| 单元/集成测试执行 | 用例结果、通过率、失败详情、耗时和有来源的测量值 |
| 代码交付 | 完整代码、运行包、研发文档、测试报告及本地 Git 交付说明 |

调研角色默认可以读取任意公开 HTTP(S) 来源，无须逐站配置。所有者可在执行设置关闭公开网页调研，或在固定配置文件限定来源域名。每次读取及重定向验证公开地址；内网、本机、登录凭据和代码执行不属于调研权限。权限在新任务派发时冻结，开启设置不自动扩大历史任务授权。

调研、产品、架构、开发、Review、单元测试和集成测试角色均可按独立模块或问题并行。阶段拆成 N 个任务时，外层仍显示一个阶段。展开后显示 N 个具名任务以及最后的“阶段名称汇总”，例如“调研分析汇总”“功能实现汇总”“集成测试编写汇总”。外层只显示该阶段的统一产物；子任务产物在内部查看。

汇总不是装饰节点：文档需要形成统一结论，代码需要真实合并和冲突检查，测试代码需要完整的可执行集合。子任务失败、合并冲突或汇总未完成时，外层不能显示已完成。

### 6.1 重试中断步骤与继续运行

执行台按工作显示工具调用次数、执行时长、小步次数的已用量与上限，明确指出耗尽的是哪一项。计量已确认但额度不足时，应提供可操作的“调整执行额度”入口，展示追加后的上限；不能只留下禁用的重试按钮。追加保留历史用量，保存后重新核验恢复条件，再由用户选择重试。计量未知时显示待核验原因，不能通过追加额度绕过核验。上一小步已保存、下一小步尚未启动就中断的工作，恢复后接着完成剩余内容。

模型响应被中断且供应商未返回完整用量时，在展开的恢复条件中说明该次请求可能已计费、用量和费用仍未知。请求计数模式下，平台核验原执行已经停止后，所有者可以明确确认保留这条未知记录并继续核验其他恢复条件；不把它改成零费用或已结算。确认本身不启动任务，不适用于必须核实金额的严格预算模式。

执行台根据真实状态提供恢复选项，并在确认前展示保留范围、重做范围和阻塞原因。

- **重试中断步骤（retry）**：重新执行选中的失败、受阻或中断工作。保留仍有效的成功上游和无依赖的成功兄弟任务；并行阶段只重试需要恢复的子任务，再形成新的汇总。受影响的后续产物、审批、代码审查和测试结论失效，必须重新取得证据。
- **继续运行（continue）**：对已暂停、没有需要先重试的失败工作、且仍有待办内容的运行恢复调度，保留现有进度。待人审内容仍等待人审，已发出的节点作业先核对，不重复派发。

恢复始终沿用原 Run 和 Iteration，累计调用次数与费用不清零，也不自动提高上限或切换不限。重试在证据充分时可使用原任务保存的代码检查点；否则使用已验证上游基线或明确阻塞。retry 创建新的执行尝试；continue 仅恢复调度，沿用身份匹配的已有执行和节点任务。两者均不恢复 Codex 临时会话中的对话状态。

需要重新测试时，平台为失败阶段建立新的执行身份；只复用版本和摘要匹配的有效构建、平台或已通过阶段证据，不能把失败节点结果当成新测试通过。相同恢复提交重放必须返回同一恢复结果，避免重复创建候选、任务或执行。

活跃 Agent 进程、执行状态未知、不能按原身份继续核对的节点作业、未核对模型调用、预算不足、损坏检查点、已交付版本及过期产品配置均需先处理。暂时无法判断能否安全恢复时，保留原证据并给出原因，不丢弃工作区或从头偷偷重建。

### 6.2 实时过程与错误恢复

每个任务提供实时执行过程，按执行次数区分本次与历史记录。用户可查看发给模型的任务指令、请求内容、可见回复、工具操作与结果、状态和耗时；支持暂停跟随、分页查看以及重试后跟随新的执行。敏感凭据脱敏，隐藏推理不展示；没有记录的历史正文明确标注缺失。

各阶段发生错误后，先进入可见的原因分析，结合有效上游与失败证据生成修复指令，再重新执行失败步骤。保留有效的已完成上游与无关并行模块，重新验证受影响的汇总、审查和测试。单元测试编写、集成测试编写及其审查同样适用；不要求用户对普通可恢复错误反复点击重试。

代码审查未通过时显示“审查未通过，待返工”，即使审查 Agent 已结束执行也不能显示为质量门禁已完成。平台默认最多安排 100 次问题所属模块修复并重新审查；用户可用 -1 持续返工、设置其他有限轮数或用 0 关闭自动返工，原有额度与人工审核始终有效。等待同版本并行审查结束属于自动返工过程，界面应明确告知等待原因。各次审查只评估该阶段已经具备的产物：后续尚未开始的测试编写不能成为初次功能审查的循环前置条件。

同一版本的并行审查全部完成后，平台合并各份报告中确认的阻断问题，一次安排所有相关模块返工；多份意见涉及同一模块时只启动一个修复任务，并保留各份意见的来源。尚未执行的审查不能被提前重置。审查汇总自身发现问题时也应退回原实现模块，修复后重新完成相关审查。

执行故障的自动重试有任务级和整轮次数上限，沿用原预算、模型与审批。未知执行、损坏证据、鉴权/额度问题或无法可靠确定责任的失败，应显示可处理的具体原因。审查必须使用前序已完成代码的准确版本；恢复检查点之间的连续提交不能被误判为未汇总的并行代码。

执行效率以减少重复阅读、重复生成和不必要的模型往返为原则。必须的产品产物、验收标准和质量门禁完整保留，用户可通过逐次调用耗时判断进展及等待原因。

### 6.3 有限响应下的完整交付

系统应允许总规模超过单次模型输出额度的代码、文档和测试计划分步完成。编码每完成一小段就保存可验证的代码检查点，全部工作完成后才进入后续验收；文档和用例表分块保存后组装成完整产物。用户可在执行过程中看到分步进展，已有确认成果不因某次响应截断而全部丢失。

单次输出上限、模型调用次数及整个任务的完成状态分别管理。不能通过无限提高输出额度、反复重做同一大任务、删掉必要需求或测试用例来规避限制。截断内容不能被视作成功，连续没有进展和额度不足应给出明确原因。检查点恢复与最终完成均保留原审批、代码审查和测试要求。

## 7. 人类可读产物

项目源码应在用户的项目目录中开发和查看。并行任务使用项目内各自独立的工作目录；阶段汇总完成后，完整代码同步到项目源码目录，执行台显示该目录。开发版本须明确区别于已通过审查、测试的交付版本。用户已有的本地修改或分支变动不得被自动覆盖，应提示处理方式。

平台自动回收已结束任务的临时运行文件，以及已确认传输完成的重复下载、构建副本。包缓存可以按容量设置保留，不能复制用户其他项目的整份缓存。仍在执行、状态未知、等待传输确认的文件，以及唯一代码快照、断点恢复资料、正式报告和交付物须保留。清理结果可追溯，失败可以重试，不影响原任务的成功记录。

### 7.1 写作范围与简洁原则

| 产物 | 内容与表达边界 |
| --- | --- |
| 产品目标说明 | 对用户原始描述补充、润色和澄清，说明使用者、价值、范围及成功标准；保留用户意图，不自行扩张定位，不加入数据库、内部接口和构建目标 |
| 市场与竞品调研 | 从产品战略和市场视角调查替代方案、竞品能力、核心竞争力、商业模式与真实用户反馈；事实、推断和未知分开，结论关联实际读取来源 |
| PRD 与需求拆解 | 使用产品语言描述功能、用户流程、业务规则、边界情形和可观察的验收标准；用户要求的外部集成可保留为需求，不展开技术实现 |
| 架构、开发计划、代码审查和测试方案 | 使用技术语言说明实现、接口、依赖、风险和验证；只提供该阶段需要的细节，不重复整份产品文档 |
| 汇总报告 | 继承所属阶段的受众和范围，综合、去重并解决分歧，保留证据；不是子报告的机械拼接 |

所有文档以简单够用为准，复杂度低的产品可以只有少量段落和必要列表。不强制空章节、不重复标题摘要、不把内部调度或机器字段混入正文。没有真实外部资料时明确“尚未完成外部调研”，不得用技术选型、虚构用户评论或捏造市场数据补足篇幅。

### 7.2 产物形式

默认产物形态只有三类：

1. 可阅读的 Markdown 文档和报告，可预览和下载。
2. 当前版本完整项目代码目录，显示准确提交及所在工作目录。
3. 项目中的单元/集成测试代码目录及其说明。

文档名称应描述内容。平台在阶段产物采集后保存相应文档到工作目录，并绑定运行、工作项、版本和原始内容摘要。文档修改或路径被替换时，保留原文件并明确报错，不静默覆盖用户改动。

JSON、原始测试报告和清单仍用于内部结构化处理与证据校验，默认产物列表不以这些对象替代报告。文档预览不执行 HTML 或脚本。PDF 可作为后续导出格式，MVP 的 Markdown 应完整可读。

## 8. 产物与质量

单元测试和集成测试分别显示：已发现用例数、通过、失败、错误、跳过、未确认、通过率、测试执行耗时和报告入口。通过率以当前候选、当前平台矩阵的有效原始用例为依据，跳过不算通过；没有执行证据、矩阵不完整或报告损坏时不得显示 100%。

代码问题显示类别、严重程度、文件、描述、来源和状态。Agent 静态审查与实际运行的检查器分别标识。未分类问题不能全部当作 bug，失败用例数量也不能直接换算成 bug 数量。独立格式检查未执行时明确说明。

性能面板展示有测试来源、单位和样本数的实际测量，例如 API P95 响应时间。测试套件耗时不是应用响应时间；没有测量时显示“未测”，不填零值或估计值。

只有代码审查、要求的单元/集成测试、平台矩阵和所选人审门禁均满足后才交付。派生 Markdown 或用户点击审核不能把失败、未知或旧版本证据改成通过。

## 9. MVP 验收

- 七个平台在创建页可辨认，多平台可表达；Web/API 可启动，未支持原生目标无法绕过服务端启动限制。
- 已有 Git 项目导入保留代码；诊断有具体依据，未知类型不伪报；名称和目标可补齐。
- 主导航独立提供“我的产品”；创建/导入后进入对应产品，使用中与已删除产品可分别查看。
- 改名与未来默认编辑不强制重跑；关键目标/平台修改产生新配置版本，保存不启动模型，单独确认后创建从目标开始的完整新运行和新迭代。
- 删除可恢复且不物理删除用户文件；恢复不自动执行，旧运行和目录归属保留，配置过期或已删除产品不能经低层操作继续运行。
- retry/continue 有明确条件和预览，保留成功上游与兄弟、使受影响证据失效；检查点、候选与重放均有身份校验，预算不自动增加。
- 页面没有锁定功能；刷新和凭据到期可自动续接，初始 bootstrap、精确 Host/Origin、票据权限、过期及控制器重启失效保持有效。
- 新需求保持原目标，建立新运行，从 PRD 开始；同项目旧文档可复用，跨项目/陈旧输入拒绝。
- 新版本使用确认基线，架构阶段仍执行，旧交付包和历史运行保持可追溯。
- 工作流能展开并行任务和汇总，外层每阶段一个统一产物，没有重复依赖表。
- 文档实际落盘并可预览，源码/测试目录指向真实版本，默认不展示机器 JSON。
- 用例通过率、问题列表和性能来源有正反例测试；无证据/旧候选/跳过/损坏报告不得假通过。
- 语言默认中文，新建/导入/需求变更可选择，旧运行语言快照和原目标不受默认值变更影响。
- 次数默认 200，`0` 正确继承并显示“不限次数”；`1` 至 `2000` 合法，负数/布尔/非整数拒绝，旧未确认提交在默认变更后仍用原值恢复。
- 产品型与技术型产物使用对应表达，聚合去重；简单项目不强制拆分或扩写。
- 工作流全图支持折行、当前运行高亮与点击查看详情，键盘和窄屏可用。
- 编码输出截断、最终格式错误与执行前提缺失分别显示；失败回执不能被当作代码验收通过。
- 重试、并发、恢复、审批和交付仍遵守同一写入者、版本、fence 和幂等约束。

实现与约束见 [MVP 架构与实现方案 v0.6](AgentFlow-MVP-产品工作台架构与实现方案-v0.6.md)。

额度耗尽时，已暂停运行可显式调额；已取消或已完成但未交付、仍有可恢复工作的运行也可调额，避免“不能暂停所以不能恢复”的死角。调额保留原状态和计数，继续执行仍需单独选择恢复操作。
