# AgentFlow 本地操作手册

日常只需要五个命令：`start`、`run`、`status`、`launch`、`stop`。长期配置统一在 `~/.config/agentflow/config.toml`，产品目标通过命令行或 WebUI 输入。

当前方案见 [PRD v0.8](AgentFlow-PRD-v0.8.md) 和 [MVP 架构 v0.6](AgentFlow-MVP-产品工作台架构与实现方案-v0.6.md)。当前受管本机路径支持 macOS 和 Node.js Web/API 产品。开发版本的真实供应商 LLM、完整产品链和原生平台验收分别记录在 [验证记录](../validation/README.md)；本文的使用步骤本身不代表验收已通过。

**当前电脑的代码、依赖和界面已经准备好，可以直接启动；真实研发需要可用的两类模型接口。** 以下工具信息于 2026-09-20 核对，模型配置和环境状态以工作台当前检查结果为准。

| 项目 | 当前本机情况 |
| --- | --- |
| 系统 | macOS 26.6.2，Apple Silicon / arm64 |
| 项目目录 | `/Users/yangyang/Documents/Work/AgentFlow` |
| Python / 专业角色组件 | 项目 `.venv` 中的 Python 3.12.14、OpenHands SDK 1.49.2 已安装 |
| Node.js / npm | Node.js 22.23.1、npm 10.9.8 已安装 |
| Git / uv | Homebrew Git 2.54.0、uv 0.12.15 已安装 |
| 编码执行器 | 本机应用附带的 Codex CLI `0.154.0-alpha.6.2`，执行接口检查通过 |
| Web 测试浏览器 | 已发现 `/Applications/Google Chrome.app`，版本 153.0.8010.50；首次准备仍会执行功能验证 |
| 工作台 | 已构建，默认地址为 `http://127.0.0.1:8787` |
| 模型 / 本机验证 | 在工作台查看当前配置、准备状态和阻塞原因 |

打开 macOS「终端」，完整执行下面四行：

```sh
cd /Users/yangyang/Documents/Work/AgentFlow
export PATH="$HOME/.local/bin:/opt/homebrew/bin:/Applications/ChatGPT.app/Contents/Resources:$PATH"
source .venv/bin/activate
agentflow start
```

第二行让终端找到这台 Mac 已安装的 Node.js、npm、uv、Homebrew Git 和 Codex；第三行启用项目环境中的 `agentflow`。这些是终端工具环境，AgentFlow 的模型、端口和研发策略仍统一保存在 TOML 中。**每次打开新的终端窗口，先执行前三行，再使用 `agentflow` 命令。** 当前安装在项目虚拟环境中，直接在未激活的终端输入 `agentflow` 可能显示 `command not found`。

启动成功会打开浏览器，并显示类似：

```text
工作台已打开：http://127.0.0.1:8787
配置文件：/Users/yangyang/.config/agentflow/config.toml
```

`start` 在后台启动平台；平台已运行时重新打开工作台。初次没有配置文件时会自动创建私有模板。看到“请配置专业角色模型 / 编码模型”时，继续第 2 节即可。

通过 `start` 打开的页面带有一次性本机启动授权，页面会移除链接中的授权片段。已有标签页刷新或 owner 凭据到期时自动续接，无需反复启动。工作台没有锁定功能；无法续接时显示“打开本机工作台”连接页，再运行 `agentflow start` 即可。关闭浏览器或退出观察终端不停止后台研发；本机任务执行期间需保持 Mac 运行和网络可用。

| 连接情形 | 页面行为 |
| --- | --- |
| 当前标签页刷新，已有票据有效 | 自动续接原控制器，恢复界面，不重建研发任务 |
| 页面内存中的 owner 凭据到期 | 使用有效票据续接；仅对明确认证失败的请求保留原幂等键重发一次 |
| 首次打开、控制器重启或票据七天未使用而过期 | 显示“打开本机工作台”，使用 `agentflow start` 的新链接 |
| 网络中断或业务结果未知 | 显示错误，不自动重新提交产品或恢复动作；先核对原状态 |

owner 管理凭据只在页面内存中。用于续接的受限票据只存于当前标签页的 `sessionStorage`，按完整 origin 和端口隔离，不存 Cookie 或 localStorage；票据只能调用 `/api/v1/session/resume`，不能直接管理产品。票据成功使用后滚动续期七天，控制器重启即失效，后台仍检查精确 Host/Origin。标签页存储不可用时当前页面可继续使用内存连接，刷新后可能需要新启动链接。

当前默认文件位置如下；修改配置中的 `data_dir`、`output_root` 或端口后，应使用修改后的值：

| 用途 | 本机路径 |
| --- | --- |
| 唯一配置文件 | `/Users/yangyang/.config/agentflow/config.toml` |
| 平台数据库、运行状态和产物 | `/Users/yangyang/Library/Application Support/AgentFlow/` |
| 默认产品输出根目录 | `/Users/yangyang/AgentFlowProducts/` |
| 平台启动与运行日志 | `/Users/yangyang/Library/Application Support/AgentFlow/controller.log` |

现有环境无需重复安装依赖。更换电脑、删除了 `.venv` 或需要重建环境时，再按第 7 节操作。

## 2. 在固定文件配置模型和默认项

配置文件固定为：

```text
~/.config/agentflow/config.toml
```

模板父目录仅当前用户可访问，配置文件仅当前用户可读写。不要把含 Key 的文件放入 Git、共享目录或日志。

### 2.1 通过工作台填写模型

在“创建产品”页面右侧的“开始前准备”中点击 **“设置模型”**：

1. “模型用途”选择 **“分析、规划与审查”**，填写模型服务、接口地址、模型名称和 API Key，点击“保存并使用此模型”。
2. 再把“模型用途”改为 **“编码开发”**，填写支持 Responses 的模型接口、模型名称和 API Key，保存。
3. 确认“分析与规划”和“编码开发”两项都显示已设置的模型，“研发模型”显示“模型与凭据已配置”。

两次保存可以使用不同供应商。如果同一模型接口确实同时支持下表两种协议，可选择“两种用途使用同一模型”，一次保存。页面保存直接写入固定 TOML；密码框提交后立即清空。

| 用途 | AgentFlow 实际调用的接口 | 配置要点 |
| --- | --- | --- |
| 分析、规划、架构、审查等专业角色 | `base_url` 后拼接 `/chat/completions` | 选择支持 Chat Completions 和原生工具调用的服务和模型 |
| Codex 编码、编写测试及修复代码 | `base_url` 后拼接 `/responses` | 需要支持 Responses 及编码工具调用的服务和模型 |

**接口地址填写 API 基础地址，不要填完整的 `/chat/completions` 或 `/responses` 请求地址。** 例如实际接口为 `https://example.com/v1/responses` 时，基础地址填写 `https://example.com/v1`。模型名称填写供应商实际提供的 API 模型 ID。Codex 在这里是本机编码执行器，研发调用使用上述 API 配置。

专业角色需要通过工具读取产物并提交结果，因此仅能返回聊天文本、不能进行原生工具调用的模型接口不够用。仅支持 Chat Completions 的接口不能直接承担当前编码用途；“兼容 OpenAI”这个服务标签本身不证明它支持 Responses。保存成功表示配置与凭据格式可用，真实服务是否接受请求由实际调用结果确认。

### 2.2 直接编辑固定配置文件

也可用本机文本编辑器打开配置文件：

```sh
open -e /Users/yangyang/.config/agentflow/config.toml
```

以下为常用配置结构。**先将模型地址、模型 ID 和 API Key 占位内容替换成自己的真实配置。** 已有模板时修改对应字段；同一文件中每个表头只保留一份，不要在末尾重复追加整段。

```toml
[app]
host = "127.0.0.1"
port = 8787
agent_concurrency = 3
# data_dir 可设为独立的绝对目录；省略使用平台默认。

[product]
language = "zh-CN"
target = "web"
review_mode = "auto"
max_model_requests = 200
# 可设为 0：不限模型调用次数；其它额度继续生效。
max_active_seconds = 1800
max_tool_calls = 100
output_root = "~/AgentFlowProducts"

[models.roles]
provider = "openai_compatible"
base_url = "https://role-model.example.invalid/v1"
model = "YOUR_ROLE_MODEL"
api_key = "REPLACE_WITH_ROLE_API_KEY"
max_output_tokens = 8192

[models.coding]
provider = "openai_compatible"
base_url = "https://coding-model.example.invalid/v1"
model = "YOUR_CODING_MODEL"
api_key = "REPLACE_WITH_CODING_API_KEY"
max_output_tokens = 8192
```

`max_output_tokens` 是用户为单次模型响应设置的有限输出额度，包含模型计入输出的推理 token。AgentFlow 不设置统一的固定最大值，应按所选供应商和模型实际支持的范围填写正数；`0` 不表示输出不限。平台通过小步执行和分块组装完成更大的任务，不要求一份完整代码或文档塞入同一次响应。

专业角色读取 `[models.roles].max_output_tokens`，编码及测试编写读取 `[models.coding].max_output_tokens`。已有运行在每次新任务执行前读取固定配置文件：当供应商、接口地址和模型名称与本轮选定的模型相同时，使用文件中的最新额度。例如从 `16384` 改成 `65536`，下一次执行即使用 `65536`，无需重建产品、重启平台或勾选恢复选项。已经派发的执行保留自己的额度，下一小步、重试及后续阶段会读取新值。执行日志的“本次模型设置”显示实际额度与来源。

SDK 自带的较小输出默认值不会压低上述额度。模型代理使用本次任务授权和模型档案共同允许的额度；不会提高旧任务的授权。修改其他供应商或模型的额度不会套用到当前模型。提高配置值不会扩大供应商模型本身的能力，供应商拒绝超出支持范围的值时会保留其错误。

示例中的 `.invalid` 地址不能调用。使用 DeepSeek 作为专业角色服务时，可将 `[models.roles]` 中的 `provider` 改为 `"deepseek"`、`base_url` 改为 `"https://api.deepseek.com"`，再填写自己可用的准确模型 ID 和 API Key；编码模型仍须满足 Responses 要求。

上例直接把 Key 放在私有配置文件中。已有的 `api_key_env` 非空行应删除，`api_key` 与 `api_key_env` 二选一。若采用环境变量方式，`api_key_env` 填的是变量名，变量必须在启动后台平台的那个终端中已导出；仅在另一个终端设置变量不会改变已经运行的平台。日常使用可以直接通过页面填写 Key。

专业角色使用原生 **Chat Completions**，编码使用原生 **Responses**。两者可以配置不同供应商、地址和模型；供应商标签不保证两种协议都支持。平台不会暗中转换协议、替换模型或把保存配置当作供应商验收成功。清空某类模型配置后，该用途会显示缺少模型，不隐式沿用旧数据库默认；现有产品仍保留自己的绑定。

手工修改文件后重启平台加载：

```sh
agentflow stop
agentflow start
```

模型表单保存即时应用模型默认并写回固定文件；手工修改的 app/product 等运行设置仍以重启为生效边界。已有产品保留选定的模型及本轮调用次数、时长与工具预算；同一模型的单次输出额度在下次执行时读取文件中的最新值。页面首次读取默认值时只初始化尚未编辑的字段，不覆盖你正在填写的本次输入。

### 2.3 选择 Web / API 和审核方式

默认 `target = "web"` 会创建带界面的 Web/API 产品。只需要后端接口时，把现有 `[product]` 中的 `target` 改为 `"api"`，重启后再提交目标。CLI 使用文件中的默认值；WebUI 会展示这些默认值，并允许为当前产品选择类型和人审方式。

WebUI 支持多选产品平台。Web 和 API 可组合；iOS、Android、Windows、macOS、Linux 显示“暂不支持”，不能以当前本机入口启动对应原生开发。导入识别到的多个平台会保留，平台声明不代表已通过执行验证。

首次体验可以保留 `review_mode = "auto"` 和其余默认限额。需要在关键阶段确认时改为 `"milestones"`，每个阶段都人工确认时改为 `"every_step"`，各模式行为见第 4 节。每个运行中的 Agent 尝试默认受 1800 秒时限约束。

`max_model_requests` 默认 `200`。CLI 不增加次数参数，使用固定 TOML 的值；页面“模型调用次数上限”允许为本次产品选择，`0` 显示为“不限次数”，刷新不会覆盖已经编辑的 `0`。

| 配置值 | 模型调用次数含义 | 其它约束 |
| --- | --- | --- |
| `0` | 不限次数，不因次数耗尽停止 | 每次输出、工具次数、执行时长及适用的费用约束继续生效 |
| `1` 至 `2000` 的整数 | 最多允许相应次数；默认 `200` | 同上 |
| 负数、布尔、非整数、数字字符串或超过 `2000` | 拒绝配置或提交，不转换成不限 | 不启动新工作 |

调用次数与费用额度分别控制。不限次数仍按供应商计费，未取得可靠费用依据时界面保持金额未知，不显示为零费用。新建、导入和后续需求会保留接受时的次数设置；修改默认只影响未来提交。

## 3. 提交产品目标

模型配置完成后，在已经按第 1 节启用项目环境的终端中执行：

```sh
agentflow run "做一个团队阅读清单，可新增书籍、标记已读、筛选和删除，重启后数据保留"
```

产品目标是位置参数。仅有两个可选的本次任务输入：

```sh
agentflow run "开发一个可新增和归档事项的页面" --name "事项清单" --output "$HOME/Products/tasks"
```

产品类型、人审、限额、模型、数据目录和端口不通过 CLI 参数指定。`product.target` 选择 `web` 或 `api`；不指定输出目录时，平台在配置的 output_root 下分配产品目录。指定目录须为空或尚不存在，不覆盖已有文件。

命令受理后显示产品 ID 并跟随进度。Ctrl-C 只退出观察，研发继续在后台执行；之后用 `status` 或页面查看。提交时连接中断，可再次运行同一命令核对原请求，平台保留恢复记录以避免重复创建。若期间改了平台数据目录，会提示恢复原目录后核对。提交标识由平台内部管理，不要求用户传标识或 JSON。

通过 WebUI 创建时，在“创建产品”填写产品名称和产品目标，确认产品类型与人审方式，输出目录可以留空，然后点击 **“开始创建产品”**。表单沿用相同模型和默认设置，并显示本次选择，无需先手工创建 Project、Plan 或节点。提交成功后进入独立“我的产品”并选中该产品，可查看当前进度、历史记录和管理操作；需要人审时点击“处理待审产物”。

命令受理后会显示 `产品：` 后跟一个完整产品 ID。后文的 `PRODUCT_ID` 均需替换为这个实际 ID，可随时通过 `agentflow status` 重新查看。

### 3.1 导入已有产品

在“创建产品”切换到导入方式，填写本机已有项目的绝对目录，先点击诊断，再补齐产品名称和长期产品目标。诊断会展示识别的平台、技术栈标志及执行限制，不运行项目安装脚本，也不覆盖源代码。

登记可执行基线需要 Git 仓库和干净提交；存在未提交改动时先提交或另行保存。未知工程不会被默认猜成 Web。当前自动迭代支持已适配的 Node.js Web/API 构建、运行和测试契约；其他工程可登记并查看诊断，但须完成执行适配才能运行。原生工程会明确显示暂不支持。

导入完成后进入“我的产品”。可选择“从头运行”从目标整理开始完整研发，也可在具备有效基线时提交需求变更；导航不再设置独立“项目与目标”页。

### 3.2 提交需求变更与查看历史

进入“需求变更”，选择产品，填写变更名称、描述和可选验收标准。变更可以增加、调整或删除功能；页面展示原产品目标，本次变更不会覆盖它。当前运行需先完成或取消，产品预览需先停止，然后提交。

流程从 PRD 更新开始，复用有效的目标、调研和架构背景，再进行需求拆解、架构影响检查、开发、审查及完整测试。小改动可以沿用架构，但架构阶段会说明判断依据；需要调整时输出新的图、接口或迁移设计。

每次需求有独立运行与预算，代码基线取同产品的已确认交付，初次导入取确认的 Git 提交。交付目录中保留旧版本，新迭代放在 `releases/<run-id>/`。需求变更与重试失败步骤含义不同，不要用重复创建产品代替迭代。

工作台顶部先选“项目”，再选“需求变更”中的初始开发或某次变更。每个项目显示一套完整工作流，所选变更决定节点状态和产物。默认从 PRD 开始的变更，前面的目标整理和调研节点显示已完成并注明沿用基线；导入项目明确显示用户输入或本地诊断来源，不代表执行过市场调研。准备中尚无运行时也能查看本次变更，不能误进入上一次运行。

项目当前文档直接保存到 `documents/<阶段>/<文档名称>.md`，没有运行 GUID 目录。提交变更时冻结已有文档，Agent 按本次变更更新完整内容，保留未受影响的需求和稳定编号；文档前部“变更记录”列出每次调整。切换历史变更时，工作台读取当次不可变快照，磁盘文件仍保持最新版本。已确认交付包不受影响。

系统在保存当前文档时整理能确认归属和内容的旧 GUID 副本。手工改过或无法核对的文件会保留并显示提示，不直接覆盖或删除；修改前可保存副本，再处理提示中的文件差异。

### 3.3 管理、删除和完整重跑

在“我的产品”搜索并选择产品。“使用中的产品”和“已删除产品”分开显示。

| 操作 | 如何使用 | 执行边界 |
| --- | --- | --- |
| 改名 | 点击“改名”后保存 | 只改产品名称，不改磁盘目录、不重跑 |
| 修改语言、默认调用次数或审核方式 | 点击“编辑配置”后保存 | 只影响未来运行；明确保存的产品默认优先于全局默认，不修改旧运行额度 |
| 修改目标或平台 | 保存后查看“需从头运行”提示 | 保存不会调用模型，旧运行只作为历史 |
| 完整重跑 | 单独点击“从头运行”并确认 | 新建完整 Run 和新 Iteration，从目标、调研、PRD直到交付，使用新的额度快照 |
| 删除 | 点击“删除产品”，确认移入已删除列表 | 保留源码、导入项目、交付目录及历史记录；目录仍属于该产品 |
| 恢复 | 在“已删除产品”中选择并恢复 | 回到正常列表，不自动运行或重置预算 |

产品预览、准备、活跃或未知执行及未核对模型调用会阻止编辑/删除，页面显示具体原因。先停止预览、暂停运行并等已有工作确认结束。关键配置编辑后必须从头运行，不能用旧阶段的完成结果代表新目标已实现；低层继续或恢复同样受此限制。

完整重跑保留原工程与历史提交，导入项目不会被模板覆盖。新的交付按运行保存在 `releases/<run-id>/`，旧包使用原名称、目标和平台快照。相同提交的确认丢失时核对原请求，不能因此重复创建完整新运行。

## 4. 自动准备、阶段进度和人审

首次产品创建会自动建立受管本机执行通道、核对工具及隔离条件、准备环境并运行内置 Web/API 验证样本。缺少条件或样本失败会明确阻塞。样本通过只说明相应环境检查完成，不能替代目标产品实现和测试。

也可先在工作台点击 **“提前准备本机环境”**，单独执行内置环境验证；该动作不调用付费模型。此按钮同时检查 Web 和 API。只做 API 产品且不需要浏览器时，直接按 `target = "api"` 提交目标，自动准备只要求 API 条件。

本机 Web 测试会自动发现已安装在 `/Applications/Google Chrome.app` 的浏览器。平台会安装锁定的测试依赖，但不会自动下载安装浏览器；更换电脑后若没有 Chrome，需要先安装再准备。首次依赖安装和构建需能访问相应软件源（包括 `registry.npmjs.org`），研发期间需能连接配置的模型 HTTPS 接口。

平台启动时及运行过程中发现已有运行正在等待受管本机作业，会自动连接该执行器并准备所需环境。浏览器、执行器或本机环境发生变化时，需要重新通过内置样本验证，随后原队列继续执行。每次平台启动后，每种所需环境最多自动尝试准备一次；先准备 API 后出现 Web 测试时，会自动补充 Web 验证。准备失败后保留原因，避免不断重复安装和测试。

如果阶段显示“等待节点执行”，执行台会显示对应本机执行器的准备阶段及失败原因。修复环境或网络问题后，点击 **“重新准备本机执行器”**；准备通过后，原来排队的作业会自动领取，无须重新创建产品或重跑上游步骤。准备按钮不代表产品测试通过；产品仍须完成自己的单元测试和集成测试。处于暂停、取消或旧进程结果未知状态的运行，需要先处理相应恢复条件。

依赖下载的等待参数可在 **本地设置 → 执行设置 → 高级执行策略 → 依赖下载无进展超时** 修改，或在固定配置现有的 `[app]` 表中添加 `package_fetch_timeout_seconds = 30`，单位为秒，修改后重启。该值用于 npm 请求等待和软件源连接的无进展截止；无数据进展的连接会退出并保留错误，避免耗尽整个构建时长。此设置属于本机网络执行配置，与模型 token 额度无关。

环境就绪后按目标整理、调研、PRD、需求与架构/任务拆解、并行开发、独立 Review、测试方案/代码、单测、集成测试和本地 Git 交付推进。工作项完成、质量通过、人审批准和 Git 已交付分别记录。公开调研默认可读取任意公开 HTTP(S) 来源；每次读取验证地址，拒绝内网与本机地址。未核实信息不能伪装成市场调研证据。

`product.review_mode` 可选：

| 值 | 行为 |
| --- | --- |
| `auto` | 默认自动推进，遇到门禁或执行阻塞时停止。 |
| `milestones` | PRD、架构和交付等关键节点等待确认。 |
| `every_step` | 本次从目标到交付的各阶段等待确认。 |

页面显示各阶段、活跃 Agent、阻塞和关联 Run。审批绑定准确版本；驳回需给出修改要求，批准不能把失败测试改成通过。研发的暂停、继续与取消使用工作台，`stop PRODUCT_ID` 专门停止交付产品的预览。

执行台外层以阶段显示目标产物和状态。阶段并行时可展开各项任务及最后的“阶段名称汇总”；外层只展示统一汇总产物。“工作项与依赖”独立表已移除，状态和产物直接在节点中查看。

已知且证据完整的 Review/测试失败可以有界返工。测试修复保留原测试和方案，再做独立 Review 与后续测试；执行未知、损坏证据、预算不足或待人审时不盲目重跑。

本机隔离测试只允许执行器分配的回环端口。单元测试自己启动 HTTP 服务时，使用 `AGENTFLOW_TEST_PORT`；持久化用例同时启动第二个产品进程时，使用 `AGENTFLOW_TEST_SECONDARY_PORT`。仅在平台外普通运行时回退到端口 `0`。测试辅助函数须在结束时关闭服务和临时资源。`listen EPERM` 应先检查这类测试启动配置，不应修改业务服务器以偷偷替换调用者指定的端口。

### 4.1 重试中断步骤与继续运行

在执行台选择需要处理的阶段，先查看恢复选项、保留项、重做范围及阻塞原因，再确认操作。

| 按钮 | 适用情况 | 平台会做什么 |
| --- | --- | --- |
| 重试中断步骤 | 失败、阻塞、取消或质量未通过，原执行已确认停止 | 为失败工作及受影响后续建立新代次；保留有效上游和成功兄弟，重新做受影响汇总 |
| 继续运行 | 本轮已暂停或已取消，旧执行已确认停止，仍有未完成工作 | 暂停时恢复原调度；取消时一次恢复全部未完成分支，为中断工作建立新代次，保留有效已完成成果与累计用量 |
| 从头运行 | 要重新执行整轮，尤其目标或平台已改变 | 回到“我的产品”单独确认，创建新的完整运行和迭代 |

取消本轮后仍可点击 **“继续运行”**。例如单元测试已通过、集成测试与代码交付已取消，恢复时保留单元测试结果，重新执行集成测试，通过后才进行代码交付。并行分支中的未完成工作会一起恢复。原进程尚未结束、结果未知或预算有待核验时，按钮会显示具体阻塞原因；取消不会跳过这些检查。

原运行的 retry/continue 不清零次数或费用，不自动提高额度，也不恢复 Codex 临时对话。重试优先使用可验证的代码检查点，必要时保留已停止工作区内原授权范围的改动；它只是新执行的起点，仍须通过审查与测试。验证失败会保留旧代码并提示原因。

已有编码步骤失败或中断时，重试弹窗提供 **“使用当前模型设置重试”**，默认关闭。手工修改模型或推理设置并重启平台后，勾选此项会将当前完整编码模型配置用于恢复范围内已规划的编码工作；未勾选时保留该工作的既有模型与推理设置。同一模型的 `max_output_tokens` 在新执行时自动读取文件，无需此选项。原 Plan/Run 绑定及旧配置历史保留。此操作不更改已开始的任务，不增加本轮调用次数，也不把旧证据改为通过。目标、调研等非编码步骤和“继续运行”没有此选项，但同样适用输出额度自动更新规则。

受影响的审批、审查和测试证据会失效，成功且未受影响的结果继续保留。仅测试执行失败而源码未变时，符合条件的构建和已通过阶段可以复用；失败测试用新的候选/节点执行身份重跑，不能把旧失败回执当成新成功。相同恢复提交重复发送只核对原回执，不重复生成候选或推进代次。

代码审查正常完成但发现阻塞问题时，平台会在原授权、额度和自动返工次数内安排修复。对于并行开发的模块，只有问题文件能明确归属于某个子任务时才自动返工该模块；修复从审查过的完整汇总代码开始，保留其他已完成模块，再重新汇总、审查和测试。问题归属不明确、需要扩大修改范围、达到返工上限或仍有人审待处理时，保留阻塞原因供处理。暂停的运行不会自动返工。

活跃 Agent 进程、未知结果、不能按原身份核对的节点作业、未核对模型调用、损坏检查点、已交付版本、有限预算耗尽或产品配置过期时，先处理页面列出的阻塞。恢复成功表示已恢复调度，不代表测试或交付已经完成。

维护 API 对应 `GET /api/v1/runs/{id}/recovery_options` 与 `POST /api/v1/runs/{id}/recover`，后者使用修订号、`retry/continue`、可选工作项及幂等键；日常在页面操作，不增加 CLI 参数。

### 4.2 执行过程、速度与自动恢复

在执行台展开一个阶段和任务，再打开“执行过程”，可以查看本次任务指令、实际发送的模型请求、可见回复、工具操作与结果、时间和调用耗时。正在查看的记录每 2 秒增量更新；可暂停跟随、加载更早内容，也可选择历史执行。当前任务重试后默认跟随新执行，手动选择的历史执行保持不变。旧版本没有记录的请求正文会明确显示缺失，不补造历史内容。

日志仅供本机所有者查看，模型凭据及常见敏感值会脱敏，不展示模型隐藏推理。正文按需展开、分页读取并压缩保存；每次执行最多记录 64 MiB 未压缩正文，达到上限会显示提示，正式产物和任务状态继续记录。日志功能不会替代完成回执、测试证据或费用账本。

发生可恢复错误后，系统先显示“失败原因分析”，读取失败证据和有效上游，形成具体重做指令，再从可核验的代码检查点重试失败步骤。有效上游和无关并行任务保留，受影响汇总和下游重新验证。单元测试编写、集成测试编写和它们的代码审查均使用此流程；审查发现代码问题时，修复原负责模块后重新审查。源码提交关系不明确时先核验实际 Git 历史，不能回退到旧代码冒充当前结果。

代码审查显示“审查未通过，待返工”时，平台会等待同版本的其他审查完成，再把各份报告中的阻断问题一起交给对应模块修复。同一个模块不会因收到多份报告而重复启动。审查汇总发现新问题也适用这一流程；只有质量通过的审查才计入完成。

测试失败后的产品修复复审如果发现已有测试代码的问题，平台会核验原测试文件的作者、写入范围、源码版本及已接受的测试计划，再交回原单元或集成测试编写任务。产品源码修复任务不会因此获得修改测试的权限。返工保留完整源码中的有效修复、原任务的累计用量、用例标识和验收标准；可补强测试数据与断言，不得删除或弱化测试。同一轮先处理单元测试问题，再处理集成测试问题，修复后的完整源码必须重新审查和测试。

工作流仍将每个阶段显示为一个节点。发生后续修复复审时，节点及详情会区分首次审查结果、当前复审状态和修复轮次；未被本次修复失效的有效测试设计显示“已完成，继续沿用”。这表示文档仍被采用，并不表示最新代码已通过测试。测试问题交回原测试编写任务后，相关复审归入对应的测试代码审查阶段。

返工指令只发给选中的任务。后续阶段因上游变化重新执行时，应根据更新后的上游产物完成自己的工作，例如单元测试编写需要覆盖已接受的全部测试计划，不能把前一步的某个功能修复当作全部任务。重试同一任务会保留它的改正指令和代码检查点。

默认每个执行失败任务最多自动重试 100 次，每个超时任务最多自动续跑 100 次，整轮执行失败自动恢复最多 100 次；重试前等待 30 秒。功能实现、单元测试编写、集成测试编写及各种代码审查的执行失败使用这些策略。审查质量不通过使用独立返工策略，默认最多 100 次，不占用执行失败重试次数。可以在固定配置已有的 `[app]` 表中调整，或在“本地设置 → 执行设置”修改，重启后生效：

```toml
auto_failure_retry_limit = 100
auto_timeout_retry_limit = 100
auto_review_repair_limit = 100
auto_test_repair_limit = 100
auto_failure_run_limit = 100
auto_failure_retry_delay_seconds = 30
```

这里的次数设为 `0` 表示关闭对应自动恢复，与 `[product] max_model_requests = 0` 表示“不限模型调用次数”不同。审查返工和测试失败修复仍支持显式 `-1` 持续到通过，已保存的配置值不会被新默认值覆盖。超时续跑同时受超时次数、单个工作次数和整轮次数限制。

达到限制时，任务提示会显示实际停止原因，例如“本任务自动重试已用 100/100 次（app.auto_failure_retry_limit）”；原始错误也会保留。连续无进展会缩小步骤并要求改变处理方法；后续轮次保留稳定的小步目标，不因超过第 5 轮而拒绝合法恢复。仍使用上述配置次数和共享时长，不设置额外的一次重试后停止规则。修改设置不清零历史计数；修复平台问题后，可通过正常“重新运行”从保留的检查点继续。

“本轮没有新增代码”不总是“没有实现”。在有完整审查返工授权的情况下，平台会核验原任务已接受的非空源码贡献、原写入范围、完整合并检查点、停止证据和累计用量。证明已有实现完整保留时，可以记录“保留已有贡献”并交后续合并和独立复审；这不代表审查或测试通过。首次空实现、证据不一致或真正的未完成代码仍按失败处理，不能通过空注释、无关格式改动或扩大权限来满足改动检查。审查意见的文件路径应指向实际需要修改的文件；缺少模块接入时，应指向调用者或接入入口。

测试执行已完成但质量失败时，产品源码自动修复默认最多 100 轮，由独立的 `auto_test_repair_limit` 控制。设为 `-1` 可持续修复直到测试通过，`0` 关闭，正整数限制累计轮数；调整后保留既有修复记录，已修复两轮的产品不会重新从零计数。每轮仍须有有效失败报告、原源码授权、剩余预算和已停止的执行；冻结测试与测试计划保持不变。模型调用未知、等待人审或预算耗尽时仍会停止。

Agent 因单次时限停止后，平台先核验旧进程及子进程已结束、代码和用量可确认，再从已保留的检查点自动开始新执行。编码工作的时长和工具用量继续累计；额度不足时，每次已授权的超时重试最多补足原工作的一份执行时长和工具额度，并留下追加记录。不会清零消耗、改动模型请求上限、增加金额预算或绕过审查、测试与人审。

模型授权使用与受管子进程一致的执行期限。准备上下文、检查隔离环境和启动握手有独立且有限的启动窗口，不会让执行授权提前到期。执行结束后旧令牌停止生效；授权确已到期时显示具体原因，不再笼统归为“Agent 执行进程异常退出”。如果累计执行时长已用尽，需要在该任务的执行额度中追加时长，再明确重试，已用记录不会清零。

Agent 启动握手默认等待 60 秒。控制端和启动器共用同一次启动时冻结的截止时间；启动器就绪后不会重新获得一段完整等待时间，重启恢复也不会延长旧启动窗口。可在 **本地设置 → 执行设置 → 高级执行策略 → Agent 启动握手等待时间** 修改，或在固定配置已有的 `[app]` 表中设置 `agent_startup_timeout_seconds = 60`，允许大于 0 且不超过 60 秒，重启后用于新启动。已有文件显式保存的 15 秒或其他合法值继续生效，升级不会覆盖。这个设置不改变 Agent 执行时长、工具额度、模型请求次数或单次模型接口等待时间。

CLI 启动本机控制器时，建立私有连接通道的等待时间单独由 `[app].controller_startup_timeout_seconds` 控制，默认 120 秒，`0` 表示不限等待。可在 **本地设置 → 执行设置 → 高级执行策略 → 控制器启动等待时间** 修改，或直接编辑固定配置文件；下一次 CLI 启动读取该值，不增加命令行选项。加载较多历史记录的 Mac 不再受原先约 30 秒的固定轮询次数限制。进程退出会立即报告启动失败；等待超时不会终止可能仍在启动的进程，也不会自动再启动一个进程。此时先查询状态或检查数据目录内的 `controller.log`，不要连续重复启动。这个设置不改变 Agent 启动握手、工作执行时长、模型请求额度或已用次数。

启动窗口耗尽后，平台先核验启动身份、旧进程及子进程已停止、没有模型调用，并确认 Agent 尚未启动执行。旧记录必须具有未发出许可的证据；新记录还可核验“许可在截止前发出，但启动器读取时已到期”的明确未启动回执，所有时钟和身份必须一致。证据完整时，任务原因和执行 Trace 会显示“Agent 启动等待超时”（`launcher_startup_timeout`），按现有执行失败自动恢复策略创建新的尝试，默认单工作和整轮各最多 100 次，并保留原尝试、回执、错误与累计恢复次数。仅看到旧的“启动未获授权”回执不足以确认超时；证据缺失、进程仍存活、调用或身份不明时保持待核验，不重复启动。启动等待本身不追加工作时长、工具或模型预算，也不会把启动失败计为代码、审查或测试质量失败。

供应商连接、读取超时或协议异常会根据实际请求记录显示具体原因；只有旧版本的未知结果记录时，不会猜测异常类型。请求结果未知不等于请求未发送，也不代表没有计费。编码回执出现已知的说明文字或完整格式包装时，平台会在保留原始文件的基础上严格提取唯一合法结果；不会补造缺失字段、把部分完成改成全部完成，或接受歧义和截断结果。

按调用次数管理的运行，超时终止窗口内产生的断连请求可以按已启用策略保留未知用量并继续：原请求仍记为未知且已经计数，新执行使用新的请求。严格金额预算中的未知费用、无法确认旧进程停止、损坏证据或无关的未知调用仍需核验，不自动重发。达到重试次数后会留下具体原因和检查点，避免无限循环。

同一轮的多个独立任务同时超时时，平台逐个核验停止回执、代码检查点和用量，并一次性预留整组所需的重试额度，避免彼此的终止请求造成互相等待。组中任一任务未满足条件时，不会部分追加授权；页面会显示具体原因。原未知请求仍保留，恢复不是重发旧请求。

macOS 编码任务的 `TMPDIR` 和 zsh 的 `TMPPREFIX` 均指向该任务已有的私有临时目录，多行 shell 编辑不依赖对系统 `/tmp` 的写入权限。源码写入范围仍由任务授权控制，未授权位置的写入会继续被拒绝。

编码工作“完成”表示所需源码已准备好接受独立验证，并不代表构建、审查或测试通过。已完成授权改动和可行局部检查后，应交给下游验证；不能仅为等待下游审查或测试而重复启动编码小步。浏览器测试的错误说明会合并 Playwright 的主错误与后续操作错误，以保留被遮挡元素、失败点击等具体线索，长度保持有界，原始报告与失败判定不变。

平台减少重复的完整格式说明和主文档写入；已完整提供的资料无需再次读取，相关材料按需读取，独立读取可以合并。上下文单页默认 24000 字符，可显式选择更小页，硬上限保持 24000；必需验收条件仍须完整覆盖。实际速度取决于模型响应、任务复杂度与重试次数，可从执行过程中的调用次数和耗时判断瓶颈。

审查等角色通过 `read_code(path, offset=0, limit=24000)` 分段读取源码；`offset` 按 Unicode 字符计数，应使用返回的 `next_offset` 继续读取，直到 `has_more=false`。源码和上下文页还会按 JSON 转义后的大小缩短，避免 OpenHands SDK 把单页中段截断；这不改变模型的 `max_output_tokens`。审查打开的源码文件存在漏读区间时，平台会要求补读后再接受审查结果。完整读取只是审查的必要输入，不能代替审查判断或正式测试。

审查草稿恢复时会携带已读取源码的清单，新执行重新完整读取相关文件再提交结论。旧版草稿如果缺少可信的阅读清单，原稿仍保留，但本次会从冻结源码重新独立审查，不复用旧结论。新格式的恢复元数据缺失、损坏或身份不符时，继续按核验失败处理。

角色工具参数错误会作为可纠正的反馈返回同一个 Agent，工具调用仍计数。例如 `result_status` 列出草稿时应省略 `result_ref` 或使用 JSON `null`；已有草稿必须使用工具返回的引用对象，不能传字符串 `"none"`。这类错误不再被当作执行组件内部故障而终止审查。真正的内部执行异常会结束当前执行，平台核验进程停止、检查点和预算后按重试配置创建新执行；损坏的草稿或结果不能因此被接受。

### 4.3 开发代码与临时文件

新建产品的源码目录为产品输出目录中的 `repository/`；导入产品使用已登记的项目根目录。并行 Agent 在项目内部的 `.agentflow/workspaces/` 各自开发。功能实现汇总完成后，`src/`、`tests/` 等代码会同步到项目根目录，执行台的汇总代码产物指向这个目录，可直接用编辑器打开。

当前开发代码使用 `agentflow/development/...` 分支，正式交付仍需通过审查、测试和配置的人审。若项目目录有你自己的未保存改动或分支已被切换，平台会保留它们并显示同步提示；先提交或另行保存这些改动，再由后续同步重新核验。历史版本和恢复检查点不因源码同步而删除。

Agent 已停止且回执完整后，平台自动清理该次执行的临时会话目录。成功的只读工作区在确认无引用、无修改后也会回收；正在回收的目录不能同时登记为新项目。节点确认构建包上传和资源释放后，会清理本地重复包；没有待执行或待重传工作时回收下载副本。正式报告、交付包、调用账本和仍被引用的源码快照保留，不应手工删除整个平台数据目录。

npm 缓存默认最多保留 256 MiB，超限后在平台空闲时回收。可在固定配置现有的 `[app]` 表中设置：

```toml
package_cache_max_bytes = 268435456
# 设为 0：空闲时不保留 npm 下载缓存。
```

配置修改后重启加载。平台不再复制用户 `~/.npm` 中其他项目的缓存。清理失败或执行状态不确定时保留文件，下次维护重试。

### 4.4 有限输出额度与分步执行

编码、单元测试编写和集成测试编写采用有界小步：一次处理一个小功能或少量用例，只返回简短的进度回执。返回“继续”时，平台核验写入范围和实际代码变化，保存 Git 检查点，再从该版本执行下一步。小步完成不会把整个工作标成完成，也不会提前放行审查、测试或人审。

一个编码工作默认最多 32 个小步，可在固定配置已有的 `[app]` 表中设置 `max_coding_steps = 32`。所有小步共用该工作的执行时长和工具额度，模型调用仍计入原运行账本。Codex 工具次数为观测计数，不宣称是执行前硬拦截；观测不完整、累计超额或已启动执行缺少计量回执时不继续。重启等待时间不计为实际执行耗时，上游修订后重新绑定正确的代码基线，累计额度保留。

为任务授权具体源码文件时，平台会先准备缺失的父目录，再在真实隔离策略下验证这些文件可写；其他模块不因此获得写权限。路径或权限不符合要求时会在调用模型前报告环境问题。小步未产生改动时，平台核验停止回执、用量和代码检查点，按照开发计划中的未完成项安排更小的下一步；成功上游与并行模块保留。连续无进展会调整重试方法；达到配置次数、未知执行或额度不足时明确报告原因，不会把空代码标成完成。自动恢复次数、等待时间和执行额度均使用设置页及固定配置中的既有选项。

目标说明、调研、PRD、架构、审查和测试计划等角色可以分块保存正文及用例数组，最后只提交小引用。平台在本地组装完整结果并校验原有格式和必要字段；阶段产物仍是完整文档和完整计划。失败时保存已经确认的草稿，恢复授权核验后可继续追加，无须重发整个文档。技术协议见 [有限输出角色协议](role-output-budget.md)。

角色文档的分块大小会依据本次任务冻结的 `max_output_tokens` 推导，不再使用固定 4 KB 分块和 16 KB 直接提交上限。例如输出额度为 65,536 token 时，分块参数最多 32,768 个转义后 JSON 字节，直接提交最多 262,144 个序列化字节；模型实际响应仍受原 token 额度约束，完整产物仍受既有 1 MiB 上下文限制。相关章节和用例可在限额内批量写入，减少中文文档的小块往返；不能通过省略内容或放宽测试适配上限。

`length` 或 `incomplete/max_output_tokens` 表示响应不完整。平台保留原始回执及实际用量，不补齐残缺 JSON、不自动封口草稿，也不把看起来完整的截断工具参数当作成功执行。推理用完全部额度时，会核验检查点并尝试更小的步骤；连续无进展会调整方法，达到配置次数或原有预算不足时，保留现场并说明原因。模型没有固定预留可见输出的保证，任何有限额度都不能保证所有任务一次成功。

### 4.5 规划输出校验与自动纠错

规划步骤提示“计划校验发现若干问题”时，平台会把具体字段问题反馈给 Agent，在原额度内修正。审查对象使用 `inspection_paths`，不应申请 `write_paths`；多组任务只有全部通过校验后才一起生效。此前出现半提交的旧运行会通过恢复机制归档未执行子任务，再修正原规划草稿，不需要重新做已完成的架构。遇到真实权限、额度或执行状态问题，工作台会保留相应处理条件。协议说明见 [规划结果校验、原子提交与恢复](planning-result-protocol.md)。

## 5. 查看、下载和启动交付

```sh
agentflow status
agentflow status PRODUCT_ID
agentflow launch PRODUCT_ID
agentflow stop PRODUCT_ID
```

`status` 查看总体状态，加 ID 查看指定产品。在“我的产品”中，只有当前配置的候选通过门禁并生成完整交付回执后，才提供“下载产品源码”和启动入口；待从头运行的配置不能借用旧交付显示成功。Git 已交付但导出失败时不会伪装成可下载。

```text
产品输出目录/
  repository/             直接新建的受管 Git 仓库；导入源码保留在原目录
  documents/              每阶段一份当前 Markdown，前部记录变更历史和处理结果
  release/                直接新建的首轮交付
    product/              已验证的运行包
    source/               精确交付源码
    documents/            研发文档
    reports/              可读测试报告
    evidence/raw_reports/ 原始测试证据
    repository.bundle     Git 对象
    delivery-manifest.json
    README.md
    start.sh
  releases/<run-id>/       新需求或完整重跑的版本交付，旧版本保留
  runtime/                与 release 分开的运行数据
```

`launch` 校验交付文件、启动受监督进程并返回独立本机 URL，产品不接收模型密钥或 owner token。服务持续观测真实进程的监听地址；核验失败撤下 URL 并请求停止，无法确认时保持未知。这不宣称能在内核层阻止所有瞬时非回环绑定或任意脱离跟踪的后代进程。

“产物与质量”默认展示 Markdown 报告、完整源码目录和测试代码目录。文档可预览、下载，代码目录可复制。单元与集成测试分别显示当前版本的通过、失败、错误、跳过及通过率；证据不完整时不会显示 100%。审查问题按缺陷、安全、格式等分类，未分类问题保留未分类。性能只显示测试报告中的实际测量与样本数，没有数据时显示未测；测试耗时不等于应用响应时间。

交付包也可按自己的 README 在 Node.js 22.13+ 环境直接执行 start.sh；用户直接运行不经过平台受管预览的监督/隔离。当前交付是本地 Git 和文件，不等于远程 push、合并或部署上线。

## 6. 阻塞、费用与关闭

- 准备失败且服务确认尚未开始研发时，在页面点击“重试准备”。已启动但记录返回丢失的 Run 会重新关联，不创建第二个；恢复待核对的旧执行不能直接重试。
- 代码已通过测试并交付 Git、仅 release/ZIP 失败时，在页面点击“重试导出”。只重新导出既有交付，不重跑模型。
- 已开始的研发失败或暂停时，使用执行台的恢复选项，区别“重试中断步骤”和“继续运行”；它们沿用原运行及累计预算。
- 连接中断先 `agentflow status` 查询；不要反复创建新目标来判断旧请求是否成功。浏览器仅在明确认证失败时续接并保留原幂等键重发；未知业务结果不自动重试。
- 模型请求次数和执行时限来自配置。次数 `0` 表示不限，其它额度独立保留；时限约束执行尝试，不保证整条迭代在固定时长完成。等待人审或节点不占 Agent 槽位，Codex 工具次数是观测限制。
- 没有可靠价格时界面费用保持未知，不显示零费用，实际计费以供应商为准。未知调用仍保留责任。

```sh
agentflow stop
```

无 ID 时停止整个本机平台；有 ID 时仅停止那个交付产品的预览。命令等待本机服务关闭，若尚未完成会提示稍后重试。

既有 Git 工程、自有节点、原生环境、原始证据、备份和恢复见 [高级 Python API 手册](advanced-python-api.md)。这些操作不扩展公开 CLI，也不把协议 fixture 或模板当成真实供应商/原生平台验收结果。

`agentflow` 应来自本项目 `.venv/bin`；这台 Mac 的 Codex 应来自 `/Applications/ChatGPT.app/Contents/Resources/codex`，Git 应来自 `/opt/homebrew/bin/git`。Web/API 路径使用项目 Python、Homebrew Git、Node.js 和 Chrome；不需要为它另行配置原生应用的 Xcode 签名或模拟器。

## 8. 常见问题与日志

| 现象 | 处理方式 |
| --- | --- |
| `agentflow: command not found` | 重新执行第 1 节的前三行，确认已启用项目 `.venv`。 |
| 页面刷新 | 已有有效标签页票据时自动续接，不需要锁定或解锁。 |
| 显示“打开本机工作台” | 首次打开、服务重启、票据过期或无法保存票据时，运行 `agentflow start` 使用新链接。 |
| 修改产品后显示“需从头运行” | 在“我的产品”确认完整重跑；不能用旧运行的继续按钮完成新目标。 |
| 产品从列表消失 | 查看“我的产品”中的“已删除产品”，可恢复；源码和历史没有物理删除。 |
| 恢复按钮不可用 | 查看“恢复前需要处理”；先核对活跃/未知任务、检查点、额度或产品配置。 |
| 缺少专业角色模型或编码模型 | 在“设置模型”中分别保存两种用途；检查模型 ID、基础地址和 Key 是否完整。 |
| Key 明明填了，但供应商返回 401 / 403 | 核对实际服务、Key 的权限及对应模型；环境变量方式需在启动平台的环境中可用，修改后重启。 |
| `/responses` 返回 404 或不支持的接口 / 工具 | 核对编码供应商是否支持 Responses 和编码工具调用，以及 `base_url` 是否误填了完整请求路径。 |
| 模型连接失败或超时 | 核对基础地址、网络和供应商状态。当前模型客户端不读取 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量，需让平台能通过当前系统网络访问所填地址。 |
| 页面提示“配置已更新，需要重启平台” | 执行 `agentflow stop` 后再执行 `agentflow start`；已有产品保留选定模型与运行预算。仅修改 `max_output_tokens` 无需重启，同一模型的新执行自动读取。 |
| TOML 格式或字段无效 | 检查引号、表头是否重复、字段名与第 2 节是否一致；保留一份 `[app]`、`[product]`、`[models.roles]` 和 `[models.coding]`。 |
| 配置文件权限错误 | 执行下方 `chmod` 命令，将配置文件限制为当前用户可读写。 |
| Codex 或 OpenHands 执行组件不可用 | 检查第 7 节的工具路径与版本，恢复锁定依赖。需要受支持的 Codex 执行接口，不能只凭“安装过 Codex”判断就绪。 |
| 工具意外提示 Xcode 许可问题 | 检查是否误用了系统 Git / Python；按第 1 节设置路径并启用 `.venv`。当前 Web/API 操作使用已验证的 Homebrew Git。 |
| Web 环境提示找不到浏览器 | 确认 Chrome 安装在 `/Applications/Google Chrome.app`，安装完成后重启平台，再点击“重新准备本机环境”。 |
| 本机环境准备失败 | 在工作台查看具体失败项，修复缺少的工具或软件源网络后重新准备；不要通过删除数据库来清除状态。 |
| 平台启动失败或 8787 端口被占用 | 先查看日志；可把固定 TOML 中的 `[app].port` 改为其他空闲端口，例如 `8788`，再停止并启动平台。 |
| 命令提交时连接中断 | 再次运行同一条 `run` 命令恢复原请求，或先用 `status` 查看；不要反复换名称或输出目录试探是否创建成功。 |
| 一直等待审核 | 在工作台点击“处理待审产物”；这是所选人审模式的暂停点，审批通过后继续。 |


## 9. 文档语言、工作流与执行错误

创建或导入时选择“文档与注释语言”，默认中文，可选 English。已有产品可在“我的产品”中、无活跃执行且预览已停止时修改未来默认；需求变更表单可选择本轮语言。CLI 没有新增参数，在固定 TOML 的 `[product]` 中设置 `language = "zh-CN"` 或 `language = "en"`。已接受运行保持自己的语言快照，既有文档不会被默认值变更覆盖。

目标说明、市场调研与 PRD 使用产品语言；架构、开发和测试文档使用技术语言。文档按实际复杂度简写，无外部调研证据时明确标注。长背景资料按需读取，仍完整保留供追溯。

执行台显示可折行工作流，当前正在执行的节点高亮。点击阶段查看产物、并行任务及汇总详情，文件路径指向工作目录；选中节点与正在执行节点可以不同。

每个逻辑阶段只显示一个节点，返工、重试和修复任务归入同一节点。主图按正常研发顺序连接；节点状态以当前执行为准，历史失败不会覆盖已经通过的新结果。点击“执行历史”可查看此前任务；“重新运行此步骤”指向当前任务。单元测试代码审查和集成测试代码审查各自保留独立节点。

`documents/<运行 ID>/<阶段>/` 中每类文档只保留一个当前文件。内容更新时沿用同一路径，文末汇总历史问题与处理情况；返工尚未完成时会明确标记，最近完成的内容仅供参考。读取现有运行时会整理系统生成的旧版本副本；被用户修改或无法核验归属的文件会保留。底层原始证据和已封存交付包继续用于追溯，新交付包内的研发文档也按阶段合并。

出现“模型输出达到上限”表示本次响应被截断；出现“最终结果不符合约定格式”表示 Agent 回执未通过校验，并不等于代码有错误。平台会自动处理明确、无歧义的格式包装：完整 JSON 代码块，以及编码进度回执中误带的 `"type":"object"` 标注。未知字段、缺少必要字段、多个结果或截断内容仍不会被当作完整结果。

编码工作声明 `complete` 后，`next_action` 中的交接说明会原样保留，但不会启动另一个编码步骤，也不能替代其他模块的完成、审查或测试。真正需要继续当前编码工作时，仍须返回 `continue` 和明确的下一步。

对历史上因此失败的编码任务，平台会先尝试**只重新收集原结果**：核对原进程已结束、工作代次、代码、原始回执和已知用量后，复用原执行与代码完成收集。不会调用模型、重置预算、改写原始回执或等待无关的并行任务。回执归一化另存为新产物，旧失败记录和新的收集记录都保留；后续审核与测试照常执行。不能明确恢复的内容仍按原自动重试策略处理；用量未知、预算已超额或证据不一致时，需要先解决具体阻塞。

本机编码环境会发现 Node 和实际 Git 安装路径，提供对应的只读运行库，使 Agent 能执行语法检查和 Git 检查。使用的工具环境不继承个人 Git 配置，也不会扩大项目写入范围或网络权限。

进程监控在 macOS 使用内核启动会话标识和原始进程出生信息，在 Linux 使用 boot ID 和进程启动 tick，避免系统时钟校正导致误判。用于展示的时间戳不单独作为新进程的身份依据。临时进程查询失败时，还会核对平台持有的原子进程生命周期。对于先前被标为“执行未知”、随后收到有效失败回执的任务，平台核验完整身份和进程结束后会自动纠正状态，再按既有规则重试；已完成的上游和历史调用记录保留。缺失、损坏、身份不符或尚未停止的执行仍需继续核验。

如果结束回执晚到，编码步骤曾被标为“用量待核验”，平台会核对该次执行的完整工具日志、结束回执、冻结任务及原账本，再补记实际工具次数和执行时长。补记只发生一次，保留原未知计量记录，不重置累计额度、不增加预算，也不把失败改成成功。其他仍有疑问的步骤和模型费用继续保持待核验。

代码审查会使用前序已完成开发任务对应的准确代码快照；快照缺失或执行代次不一致时会明确提示，不会回退到初始代码。出现“启动前的隔离检查超时”表示检查尚未完成，Agent 没有开始审查，不能据此认定功能实现失败。隔离探针单次默认等待 30 秒；只有明确的权限拒绝才算否定检查通过，超时或其他错误仍阻止启动。平台确认未创建执行器、没有模型调用且身份匹配后，可在当前代码审查步骤选择重试，保留已经完成的功能实现。

“确认尚未启动”和“启动后回执缺失”使用不同的恢复判断。已有进程、启动许可、未核对调用或损坏证据仍需先核验，不能通过重试重复启动。

`reasoning_output_limit` 表示本次响应的推理消耗了全部单次输出额度，尚无可执行的正文或工具调用。平台会先核验代码进展，再用更小的小步恢复；第一次无进展最多允许一次缩小后尝试，再次无进展即暂停。`max_model_requests = 0` 只取消调用次数上限，不会提高单次 `max_output_tokens`，也不会减少模型的推理消耗。无需先把额度提高到很大才能使用分步恢复。

如需主动调整推理开销，使用支持该选项的 Responses 编码模型时，可在固定 TOML 现有的 `[models.coding]` 表中设置推理强度。它是可选模型设置，不替代分块与检查点机制。以下是字段示例，不要重复添加已有表头：

```toml
[models.coding]
reasoning_effort = "low"
```

未显式配置时，平台不指定推理强度，实际行为取决于编码执行器及供应商的默认设置。不同供应商对各强度取值的支持和含义可能不同，应以已核实的接口说明及实际响应为准。设置 `low` 不保证输出一定完整或代码质量通过，后续仍需审查与测试。

推理设置保存后执行 `agentflow stop`、`agentflow start` 加载，再在失败编码步骤的重试弹窗中勾选 **“使用当前模型设置重试”** 并确认。全局配置不会自动替换旧 Run 的模型或推理强度。若只调整同一模型的 `max_output_tokens`，直接保存即可在下一次执行生效。若继续截断，可检查模型允许的单次输出额度或拆小任务，不能通过增加调用次数来解决单次响应上限。

若显示“本轮模型调用次数已达到配置上限”，说明某一层有限次数额度已耗尽，修改固定 TOML 只改变未来运行。当前运行需要所有者明确调整调用额度；操作前先暂停并确认任务结束，保留已使用次数，不清零账本。成功后仍保持暂停，随后根据恢复选项重试失败阶段或继续调度。平台不会自动增加上限或切换不限，调用仍按供应商计费。

| 当前次数额度 | 显式额度操作 | 结果 |
| --- | --- | --- |
| 本轮为有限值 | 提高为 `1` 至 `2000` 中更大的整数 | 提高本轮上限；迭代为有限值时增加同等次数，已不限则继续不限 |
| 本轮或迭代仍有有限上限 | 将本轮目标设为 `0` | 本轮与迭代均不限次数，保留全部已用计数和费用记录 |
| 本轮与迭代已经均为 `0` | 用新提交标识再次请求 `0` | 拒绝无变化操作；原提交标识的重放仍幂等 |
| 本轮已为 `0` | 改成有限值 | 追加接口拒绝降低额度 |

这些操作不改变每次输出额度、工具次数或执行时长，也不会自动恢复调度。

已取消或已完成但尚未交付的运行，如果仍有失败或中断工作且额度耗尽，可以在执行台先显式调整本轮上限，再重试。调额不把已取消状态改成运行，也不启动模型；已交付或没有可恢复工作的运行不能借此重开。

如果失败的是编码、单元测试编写或集成测试编写，并显示 `coding_budget_exhausted`，在执行台查看该工作的“执行额度”卡片。卡片分别列出工具调用次数、累计执行时长和小步次数的已用量、上限、剩余量，并标出耗尽项；工具次数按实际观测记录，超过原上限时也会显示超额量。这些是同一工作跨小步和重试的累计额度，独立于模型调用次数与单次输出上限。

1. 确认原执行已结束；按卡片中的阻塞说明处理运行状态与证据问题。
2. 点击“调整执行额度”，填写需要追加的次数、秒数或小步数以及原因。`0` 表示该项不追加；追加后各项须保有可用余额，历史用量不会清零。
3. 保存后等待平台重新检查恢复资格。只有检查通过才可点击“重试此步骤”，确认后从有效进度继续；保存额度本身不会启动模型。

显示“待核验”时，用量不能按零计算，也不能通过追加额度跳过核验。先核对原执行和用量回执，再“重新读取额度”。若编辑期间状态或额度版本变化，请返回重新读取；若提交结果因连接中断尚未确认，使用“核对原追加提交”重查同一操作，避免重复追加。

如果模型响应因执行超时或中断而没有完整用量回执，供应商可能已经计费，原调用次数、未知用量和未知费用仍保留。符合上文超时续跑策略的 `request_limited` 运行，会自动记录策略授权并继续，无须再次手动确认。已确认的历史调用不再逐条显示；仍需处理的调用集中在默认收起的“处理恢复条件”入口中，展开后可核验并确认。

这项确认不会将调用记为已结算、不会退款或清零计数，也不会启动任务。确认后仍要重新核验其他阻塞；若编码工作累计时长已经耗尽，先显式追加工作额度，再确认重试。严格金额预算、执行仍存活、恢复证据不完整或编码工作计量未知时，不能通过这一入口绕过核验。确认回执丢失时，“核对原未知用量确认”复用原调用、版本和提交标识。

确认仅适用于被核验的调用版本与停止证据。后续记录或恢复证据变化导致原确认失效时，页面恢复阻塞提示并要求重新核验；历史确认不会覆盖当前状态。

## 执行设置与限制来源

公开调研可在 **本地设置 → 执行设置 → 高级执行策略 → 公开网页调研** 开启或关闭，默认开启，保存后重启生效。也可在固定文件 `~/.config/agentflow/config.toml` 现有的 `[app]` 表设置：

```toml
research_public_web_enabled = true
research_web_hosts = []
```

空来源列表表示允许任意公开来源，无须逐站登记；需要限定范围时可填写域名，例如 `["example.com", "docs.example.com"]`，重定向后的站点也须在列表中。显式关闭开关时，即使列表不为空也不允许读取。启用只授权新派发的调研任务，旧任务不会自动扩权；重新执行调研须通过正常恢复或新一轮流程产生新授权，历史来源与未验证结论保留。

网页读取仅支持公开 HTTP(S) 标准端口，不使用登录状态或个人/模型凭据，不访问本机和内网。网页中的指令不获得执行权限；来源读取失败时保留失败原因，不能把推断记成已核实事实。

在 **本地设置 → 执行设置** 修改应用层额度。面板按“常用工作额度”和“高级执行策略”组织，显示每项的固定文件值、本次服务已加载值、应用默认值、单位、零值含义和生效范围。固定文件仍是 `~/.config/agentflow/config.toml`；界面提交只修改选中的应用字段，保留模型配置、凭据及其他未修改项。

| 限制 | 固定配置来源 | 应用默认值 | 含义与生效边界 |
| --- | --- | --- | --- |
| 每次模型输出长度 | `[models.roles].max_output_tokens`、`[models.coding].max_output_tokens` | 以模型配置为准；未填写时默认 8192 token | 含推理和可见输出。执行设置中只读展示，修改使用模型设置。同路由新派发读取当前文件值，已派发任务保留原授权。 |
| 模型推理强度 | `[models.coding].reasoning_effort` 等适用模型配置 | 未显式配置时不覆盖供应商/执行器行为 | 不在应用执行设置中另建同名参数。模型或推理设置的切换遵守既有模型选择与重试策略。 |
| 单次模型接口请求超时 | `[models.roles].request_timeout_seconds`、`[models.coding].request_timeout_seconds` | 未填写时 120 秒 | 模型代理按选定模型配置请求供应商；这是一次接口请求的等待时间，不替代 Agent 工作的累计执行时长。 |
| 模型请求/响应字节容量 | `[models.roles/coding].max_request_bytes`、`max_response_bytes` | 未填写时 8 MiB / 16 MiB | 保留在对应模型的固定文件配置中；约束协议传输大小，和 `max_output_tokens` 分别生效。 |
| 每轮模型调用次数 | `[product].max_model_requests` | 200 次 | 新运行的默认次数预算；`0` 表示不限次数，仍保留计量。已有运行使用执行台的显式调用额度调整。 |
| Agent 工具调用额度 | `[product].max_tool_calls` | 100 次 | 专业角色按单次尝试限制；编码工作在多次小步和重试间累计。`0` 表示没有工具调用额度，不是无限。 |
| Agent 执行时长额度 | `[product].max_active_seconds` | 1800 秒 | 专业角色按单次尝试限制；编码工作跨尝试累计。不是排队时长，也不是每次重试重新获得 1800 秒。 |
| 编码工作小步额度 | `[app].max_coding_steps` | 32 步 | 重启后首次建立额度的新编码工作使用此值；已有工作累计步数和已批准上限保留。 |
| 专业角色执行循环上限 | `[app].max_role_iterations` | 1000 轮 | 重启后新派发的专业角色尝试使用该配置。1000 是可修改的默认值，不再作为额外隐藏截顶；它独立于模型输出长度。 |
| 公开网页调研 | `[app].research_public_web_enabled`、`[app].research_web_hosts` | 开启；来源列表为空 | 空列表允许任意公开来源；非空列表限制域名。开关在高级执行策略中设置，重启后生效；开启不会扩大旧任务授权。 |
| 同时执行的 Agent | `[app].agent_concurrency` | 3 个 | 重启后的调度采用新值，包括已有运行中尚未派发的工作。 |
| 审查自动修复 | `[app].auto_review_repair_limit` | 100 次 | `-1` 持续到审查通过，`0` 关闭，正整数限制轮数；所有模式保留原执行额度、未知责任与人审门禁，历史次数不清零。 |
| 测试失败后的源码自动修复 | `[app].auto_test_repair_limit` | 100 次 | `-1` 持续到测试通过，`0` 关闭，正整数限制累计轮数；保留原源码授权、冻结测试与计划、模型、预算和人工审批门禁，历史次数不清零。 |
| 单个工作自动恢复 | `[app].auto_failure_retry_limit` | 100 次 | `0` 关闭单个工作的自动恢复；提高设置不会清零已发生的恢复次数。 |
| 超时自动续跑 | `[app].auto_timeout_retry_limit` | 100 次 | `0` 关闭；受单工作/整轮恢复次数共同限制。核验停止与检查点后，按策略保留未知用量并补足下一次原时长/工具额度，累计消耗不清零。 |
| 每轮自动恢复总次数 | `[app].auto_failure_run_limit` | 100 次 | 所有工作自动恢复的总计；`0` 关闭整轮自动恢复，历史计数保留。 |
| 自动恢复等待时间 | `[app].auto_failure_retry_delay_seconds` | 30 秒 | `0` 表示不额外等待，不表示关闭恢复或不限恢复次数。 |
| 节点单次作业时长 | `[app].node_active_seconds` | 1800 秒 | 重启后新派发的节点作业使用，独立于编码工作的累计时长；已派发节点任务保留原授权。 |
| 依赖下载无进展超时 | `[app].package_fetch_timeout_seconds` | 30 秒 | 重启后用于本机 npm 请求及软件源代理等待数据的截止时间；代理发送背压仍由作业总时长限制。可在高级执行策略中调整。 |
| Agent 进程日志容量 | `[app].agent_max_log_bytes` | 16 MiB（16,777,216 字节） | 约束执行进程保存的日志量，不是模型输出 token 数；重启后新启动的执行采用。 |
| Agent 启动握手等待 | `[app].agent_startup_timeout_seconds` | 60 秒 | 控制端与启动器共用同一次启动的截止时间；独立于工作和模型额度，重启后新启动采用。已有显式值保留。 |
| 控制器启动等待 | `[app].controller_startup_timeout_seconds` | 120 秒 | CLI 等待本机私有连接通道就绪；0 表示不限等待，进程退出仍立即失败。下一次 CLI 启动采用，模型和任务额度不变。 |
| 执行隔离检查等待 | `[app].isolation_probe_timeout_seconds` | 30 秒 | 隔离探针的等待时间；超时仍不能假装隔离检查通过，重启后采用。 |
| 节点作业输出容量 | `[app].node_output_limit_bytes` | 256 MiB（268,435,456 字节） | 新节点作业的输出容量约束，独立于 Agent 日志和模型输出长度；重启后新派发作业采用。 |

界面中的允许范围来自同一份后端配置校验，不根据这张默认值表限制用户输入。例如，显示“100 次工具已耗尽”应检查工作账本和 `product.max_tool_calls`，不能通过调整模型的 `max_output_tokens` 解决；累计 1800 秒只剩 21 秒时，直接重试也只会获得已确认的余额。

操作步骤：

1. 修改需要调整的字段并点击“保存执行设置”。未保存输入会在定时读取、手动重新读取和切换工作台页面时保留。
2. 保存写入固定 TOML 文件，页面明确显示待重启状态。按平台正常停止、启动流程重新加载；各项具体生效范围见面板说明。
3. 已有运行的模型调用账本、已建立的工作额度和累计用量不会被这次保存重置。当前工作需追加额度时，点击“前往执行台调整当前工作额度”，核对实际用量后执行显式追加与重试。

文件被其他编辑修改时，页面保留你的输入并阻止直接保存。先核对“开始编辑时 / 当前文件 / 你的修改”，选择“采用当前文件版本并保留我的修改”只更新编辑基线，仍须再次点击保存。未修改的字段继承当前文件值。

网络中断或回执无法确认时，输入保持冻结，“核对原保存”复用原内容和原提交标识。核对已成功的历史保存后，页面会重新读取当前文件，避免用旧回执覆盖后续修改。若服务明确报告原保存无法确认，可只读核对当前文件并选择“以当前文件为准”结束本地待确认表单；此操作不再次写入文件。

内置 Node/Web/API 工程的构建与测试支撑文件未修改时，平台可从已接受的目标及测试计划自动生成执行配置，无需额外编写 `agentflow.project.json`。项目已有有效清单时使用该清单；文件无效、自定义工具链或支撑文件发生变化时，仍需提供明确清单。这个项目级清单描述如何构建和测试，不是上述全局执行额度的配置入口。
## 审查中的既有测试迁移

需求变更使旧测试期望失配时，代码审查会自动分析修复归属。工作台在原代码审查节点内展示“问题归属分析”“既有测试契约迁移”“生产代码修复”“修复结果合并”“既有测试诊断”和“复审”，不增加新的主流程步骤。

只有已接受需求明确批准的行为变化才能更新测试期望；实际产品回归仍修复生产代码。原用例名称、断言操作及无关测试保持不变。诊断通过后仍须通过独立审查，后续正常测试阶段继续完整执行。

无需新增 CLI 参数或重试配置。返工沿用已有的审查修复次数、执行时长、模型额度及人工审核设置；迁移用量累计到原测试作者。遇到“待审批”时在原审核入口处理；遇到具体权限或需求依据问题，查看节点内的归属分析及错误详情。暂停、取消、恢复继续使用现有运行控制入口。

当前自动迁移适配器支持内置 Node Web/API 项目的 Playwright 精确期望断言，以及 ESM 导入的 Node 严格相等断言。已有 Node 单元测试会纳入诊断；未实现的 starter 单元占位不会提前变成质量门禁。同一处修改被重复发现时只编辑一次，所有意见继续保留。其他测试形式会保留明确原因，不能通过放宽断言或修改测试运行配置自动放行。
