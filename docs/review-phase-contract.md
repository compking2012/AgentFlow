# 代码审查的阶段契约

`code_review` 同时用于功能实现后的首次审查，以及单元、集成测试代码生成后的独立审查。它们共享质量门禁，但不能共享“所有测试已经生成”的前提。否则首次审查会等待自身下游的测试阶段，自动修复也无法在只授权 `src/`、`public/` 的功能开发子任务中补写测试。

控制器在 `domain/review_phase.py` 根据当前依赖图推导 `review_phase_contract`，不根据任务标题、子任务 `goal`、旧审查结论或存储的旧契约推断阶段。契约记录最近的代码产出者及版本、原始写入范围、当前必须完整审查的测试阶段和仍在下游的测试阶段。已接受的复用测试在本轮计划重新生成时仍作为回归基线，不能提前满足或提前触发新一轮测试实现的完成条件。

首次功能实现审查检查生产行为、接口和冻结边界。尚未进入的测试阶段缺少新用例、框架 ID 或仍有未修改的 starter 测试，本身不能作为功能代码的阻断缺陷。任何阶段都必须保留对现有测试删除、断言弱化、真实回归、测试支持文件篡改的审查，不能根据路径直接过滤 findings。单元测试生成后的审查完整核验单元用例；集成测试生成后的审查继续保留已生成单元测试的义务，并完整核验集成用例、精确框架 ID、断言、边界和异常场景。静态审查不等于执行报告。

`StageContext` 每次派发重新派生契约，契约也参与上下文目录身份。`Scheduler` 将它和冻结的 `source_commit` 保存进 `dispatch_context.task`；`RuntimeService` 保留到 `TaskEnvelope`，并由 OpenHands 的 `system_message_suffix` 提供高于子任务正文的审查约束。现有运行中的旧子任务可以保留原始标题与 goal，通过正常版本修订后的重新派发得到当前契约。没有契约的历史冻结派发记录继续按原记录保留，不在恢复时偷偷改写。

新开发计划获得每个可展开阶段的结构化说明。新 `code_review` 子任务必须声明 `review_focus`：

| 值 | 可用条件 |
| --- | --- |
| `current_code` | 当前冻结代码的行为、契约、安全等审查 |
| `existing_test_regressions` | 已有测试与测试支持的回归检查，所有审查阶段可用 |
| `unit_test_coverage` | 该审查的代码祖先已经包含单元测试实现阶段 |
| `integration_test_coverage` | 该审查的代码祖先已经包含集成测试实现阶段 |

其他阶段不声明该字段。`StageExpander` 在写入子任务前原子校验范围，缺失时返回 `review_focus_required`，跨阶段时返回 `review_phase_mismatch`。自然语言 goal 只能细化合法范围，不能扩张契约；聚合审查仍负责该阶段的全部必需检查。系统不靠猜测中文或英文任务描述中的关键词分类。

本修改不删除、降级或自动通过已返回的 blocking findings。已有错误审查必须通过正常 revisions 重新审查，获得绑定当前源码版本的新证据。历史证据仍可追溯，真实问题继续进入原有质量门禁。

回归测试覆盖旧 `cr-tests` goal 与真实 producer 冲突、阶段展开拒绝、生成后测试完整性义务、复用测试基线、实际派发持久化和运行时系统指令传递；所有测试使用临时 Store、Git 仓库和本地 fixture，不接触运行中的真实数据库或模型服务。

## 既有测试契约迁移

当审查发现旧测试与已接受的新需求不一致，控制器在当前审查节点内部建立返工批次。只读的 `review_disposition` Agent 对照原审查、需求版本、冻结提交和既有断言，分别记录发现问题的路径和实际修复路径。每条阻断意见都必须有处置，分析不能直接豁免意见或判定审查通过。

生产缺陷交给原计划中的实现负责人。只有引用了已接受需求及原文依据的行为变更，才交给独立测试迁移 Agent；其写权限来自原测试作者的授权范围。正常单元、集成测试设计与编写阶段保持原有顺序，不因迁移任务完成而提前完成。

迁移契约绑定文件、原用例标识、断言标识、匹配操作、旧期望、新期望及需求依据。自动迁移支持 Node Web/API 项目的 Playwright 精确期望操作：`toBe`、`toEqual`、`toStrictEqual`、`toContainEqual`、`toHaveText`、`toHaveValue`（包括 `resolves`/`rejects`），以及通过 ESM 导入的 Node `strictEqual`、`deepStrictEqual` 和 `node:assert/strict` 的严格别名。Node 断言只允许修改第二个期望参数；实际表达式、消息及操作保持不变。被重定义、转交给其他代码或遮蔽的断言绑定，以及展开参数，不能通过该适配器迁移。其他断言形式返回明确的不支持原因，不用字符串替换绕过校验。

平台使用随包分发的 Babel 解析器读取语法树，不执行待检查代码。安全核验读取不可变 Git 提交的导出副本，只允许指定断言的期望参数改变，保留测试标识、实际表达式、匹配操作、无关断言、注释、测试配置及其他文件。不得删除对象约束、数组成员、测试用例或添加跳过。解析器和许可证随 AgentFlow 安装，不依赖工作台开发依赖目录。

返工任务、权限、源码基线、归属记录、原审查的复审依赖和规划完成回执在同一事务中提交。每个辅助任务有独立执行身份，继承原作者的人工审核要求；编码用量继续计入原作者额度和本轮模型账本。重复回执不会重建任务或重复记账，未知用量在证据补齐前仍阻止新的执行。

修复分支合并后，再次核验合并提交中的测试内容与通过保护检查的分支一致。诊断节点运行原 Web/API 测试套件，并在存在已实现的 Node 单元套件时运行该套件。单元用例从冻结的 `tests/unit.test.mjs` 及其静态本地测试模块导入中发现，以实际 JUnit 用例身份核验；原样 starter 占位不作为既有回归要求。诊断结果单独保存在 `review_diagnostic`，不创建正式测试检查、候选版本或交付记录。真实用例失败进入新的只读归属分析；执行身份、需求或权限无法核验时保留具体原因。诊断通过后，原审查子任务及汇总统一审查同一个新提交。独立复审通过之后，才放行后续正常阶段。

工作台仍只有一个代码审查节点，节点内显示归属分析、测试迁移、生产修复、合并、诊断及复审任务，并分别显示质量失败、返工中、待审核和复审中。被替代的批次与原意见作为历史保留。暂停不派发新任务；取消先停止并核验相关节点作业，再完成诊断取消，可通过正常恢复入口继续。

## 审查返工中的执行恢复

同一工作执行超时或结果格式失败后的 `retry` / `continue` 不构成新需求。恢复事务从已经核验且原子重检的原工作记录保留 `payload.change_expectation`，将当前恢复操作原因单独放入 `payload.recovery_instruction`。任务指令分别展示修改要求与执行恢复建议，角色草稿恢复提示也属于执行建议。后续 partial coding step 沿用这些字段。真正的用户 revisions 仍替换修改要求，并清除旧执行恢复建议，避免旧范围混入新任务。

受管工作区在审查返工中可能只读取了代码，超时前没有产生新 diff。此时仍须保留已核验的原 `source_commit`；空 diff 不能导致丢弃审查基线并回到项目初始提交。恢复记录绑定原执行、派发源码、允许写入范围与原 `repair_base_snapshot_id`；对并行返工同时核验 alias 的子任务范围和版本。再次取源码时重新核对这些绑定。保留空 diff 的来源不表示代码已修改或质量已通过，原审查缺陷仍须修复并重新独立审查。

若返工在派发前停止，则只从当前授权的审查快照及其已完成的原代码执行建立恢复来源；并行 alias 必须对应原子任务执行和原写入范围。缺少身份或范围证据时停止恢复，不降级选择项目初始版本。

`control/review_checkpoint.py` 还校验返工授权链：`review_repair.checkpoint_alias_ids`、原审查与审查执行、原聚合快照及执行、alias 的 `source_snapshot_id` 等来源字段、原子任务贡献与执行必须相互对应。alias 的提交、树、基线和仓库必须与原被审查聚合快照一致；Git 对象完整并不能替代这项授权检查。历史记录可以已标记 stale，但不能与授权链脱离。恢复事务的原子重检包含 `review_repair`，后续复用保存的审查来源时也重新校验授权链。

`test_recovery_correction_context.py` 使用真实审查返工、临时受管 clone、超时恢复和下一次 TaskEnvelope 验证上述路径，并验证并行模块保持完整、篡改来源/范围/alias 版本被拒绝，以及 partial 后再次超时仍能读到原修改要求。

## 多条意见与后续测试修改

同一断言被多个审查发现引用时，保留全部意见及需求引用，将完全一致的迁移合并成一个实际编辑；不同新期望不能任意取其一，须先解决冲突。代码和测试修复合并、诊断与独立复审完成后，正常测试编写阶段从最新合并源码继续。其累计预算包含此前委派迁移用量，代码差异基线使用当前工作来源，两者分别处理。

自动契约迁移仍是受控的字面量期望更新，不授权删除用例、改变实际表达式、改写 mock 或测试运行配置。需要这些改造时，应提供明确的测试改造方案及授权，不能以降低测试要求代替修复。

## 测试覆盖补齐与上下文协议 v2

`test_coverage_extension` 在同一返工流程中补齐已接受测试方案要求的既有用例覆盖。同一阻断意见可以分配给不同的原作者，例如生产界面负责人及 Web 测试作者；同一意见与同一作者不能重复分配。单元作者必须引用已接受的 `unit_test_plan`，集成作者必须引用 `integration_test_strategy`，引用绑定文档版本和准确原文。测试方案不能作为测试期望迁移的授权来源。

同一文件不能在一个批次中同时安排期望迁移与覆盖补齐，因为组装结果必须完整等于各自受保护的子提交；这种重叠会在归属校验阶段拒绝，不授权未经核验的双重合并。不同文件可以采用不同保护类型，但同一原作者的辅助动作依次执行，其他作者保持并行。

覆盖任务使用原作者的普通 `unit_test_implementation` 或 `integration_test_implementation` 步骤，只能写入分配的既有测试文件。原作者审批策略及累计预算继续有效。只允许在原用例回调语句块尾部追加语句，并按需增加无顶层执行副作用、不会遮蔽旧绑定的新助手声明。已有语句、断言、助手、用例名称、运行操作、配置及支撑文件均受保护；禁止替换断言期望、跳过用例、修改旧绑定或提前退出。

每次辅助编码准备还要核对原作者池的当前剩余额度和其他未结算小步预留，实际执行上限取子任务与作者可用额度的较小值。已有无启动证明可以释放未使用预留，未知用量不能释放。正常超时续跑沿用原策略，在同一事务中将子任务所需的额度增量同时加入原作者池；超时审计绑定两者身份、旧新限额及未改变的已用计数，幂等重放不重复追加。

控制器从不可变 Git 提交导出基线及子任务结果，由 `TestCoverageGuard` 检查后写入 `test_coverage_check`。回执绑定批次、工作项、代次、上下文摘要、提交和树身份，并且不可被另一结果覆盖。组装后的每个授权测试文件必须与对应已核验子提交具有相同 Git blob 和文件模式，否则不能开始诊断。结构保护只证明既有测试得以保留；独立审查仍须核验新增断言确实覆盖原意见和方案。诊断不替代原正式测试门禁。工作台将这类工作显示为“测试覆盖补齐”并统计处置数量。

新建分析上下文带有 `protocol_version: 2`。旧 `triaging` / `needs_attention` 批次只有在从未创建修复任务、原分析全部历史执行及进程停止证据均已核验时，才能调用 `upgrade_triage_context(batch_id)`。控制器基于同一原源码、原审查及原已接受文档重建证据，仅补充当前已接受测试方案；任何原证据变化、未知执行或修复派发都拒绝升级。事务重新核验停止状态后，将完整旧上下文、摘要、原批次状态和修订号保存到只写一次的 `review_contract_context_history`，再替换当前上下文及其摘要。

协调器即使在运行暂停时也可进行该证据升级。成功升级将批次置为 `triaging`，保持原分析工作项 ID、工作状态、代次、尝试记录、重试次数、审批与预算不变，不派发任何任务；通过现有恢复入口重试原阻塞分析。仅接受 `blocked`、`failed`、`cancelled`、`pending` 或 `queued` 的原工作项；已经成功完成并要求澄清的分析不能自动升级成不可重试的中间态，原 `needs_attention` 保持不变。重复协调不会新增历史、任务或额度，旧派发上下文继续保持原样。升级入口只处理控制器证据，不直接修改任何生成产品或运行设置。
