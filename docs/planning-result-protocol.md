# 规划结果校验、提交与恢复

目标整理和开发任务规划可以提出多组并行任务。模型提交的是建议，控制器依据已接受计划决定哪些建议可以生效。

## 范围与权限

- `write_paths` 表示实际写权限，只能用于功能实现、单元测试编写、集成测试编写，且必须处于原阶段授权范围内。
- `inspection_paths` 是可选的检查对象，不授予读写权限。代码审查和测试代码审查使用该字段标明文件，`write_paths` 必须为空。
- `review_focus` 必须属于该审查阶段的允许范围；未来测试阶段的验收要求不能提前变成当前生产代码审查的前提。

调度器冻结 `planning_contract`，包含可拆分阶段、阶段身份与版本、授权写入范围、审查类型和图规模限制。缺省不序列化此字段，保持旧任务身份兼容。提交时还要依据当前数据库状态重新核验。

## 结束前纠错

普通 `finish(result=...)` 和分块 `finish(result_ref=...)` 在发布最终结果前使用同一个计划语义校验器。校验器一次返回全部问题，包括错误码、阶段、子任务、字段位置及修正要求。

校验未通过时，受管 Agent 保留草稿并继续修正。对于已封口的长文档，`result_revise_parallel_work(result_ref, parallel_work, request_id)` 派生新草稿，只替换任务计划，原正文与原草稿不变。小数组可以直接提交；传入 `parallel_work=null` 时重开该数组，通过原有 `result_append` 分块补齐、封口，再调用 `finish`。这些操作继续消耗原有工具与模型额度。

## 原子提交

控制器先在内存中构造并校验完整工作图，再在一个 SQLite 写事务内完成全部任务展开、展开回执、规划提交回执、产物登记以及规划工作完成状态。任何一组无效、版本变化或后续写入失败，整批回滚。

`planning_commit` 绑定规划 attempt、代次、原始结果摘要与批次摘要。重复结果不能重复创建子任务；原始结果中的 `parallel_work` 必须与待提交批次一致。文件存储中的原始结果和准备好的可读文档可以提前持久化，但它们不表示工作图已接受。

## 故障与恢复

`failure_diagnostic` 保留原始控制器错误码、可公开消息及结构化细节。计划输出错误使用 `planning_validation_failed`；仅明确的规划版本变化使用 `planning_state_changed`。真实权限、预算、身份和进程状态错误保持各自限制。已知供应商和启动错误继续使用安全文案，公开诊断按日志规则隐藏凭据。

可纠正的计划输出在当前步骤重试，继续使用设置页面和固定配置中的自动恢复策略，不额外增加隐藏重试上限。超时或退出后，可将已核验完整结果作为新 attempt 的草稿导入；原执行结果、用量、模型设置和审核要求保留。只有确实准备重试且其他恢复条件满足时，才显示冷却时间。

历史半提交通过正常恢复机制处理：归档尚未执行的旧子任务，恢复其汇总阶段，再重新提交完整计划。已完成上游保持不变。历史 `role_write_scope` 错误仅在规划身份、原始结果和回执匹配时细化为计划输出错误，不适用于实际代码越权。
